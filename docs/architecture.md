# New ComfyUI Frontend: Architecture Plan

Status: proposal (researched against ComfyUI backend, ComfyUI_frontend, and KJNodes/rgthree sources; stress-tested via design review)

See also [hazards.md](./hazards.md): the load-bearing invariants (reroutes especially) that keep the old frontend's minefields defused, and the failure mode each one prevents.

## Goals

- Performant node-graph editor for ComfyUI, local-first (no cloud/API-node concerns for now).
- Full V3 node schema support: MatchType templates, Autogrow, DynamicCombo, DynamicSlot, multi-type unions, remote combos, lazy/hidden inputs, price badges (later), previews.

Canvas slot language distinguishes type families at a glance, built from four independent visual axes that always compose. SHAPE carries cardinality: definitely-scalar pins are circles, definitely-list pins are diamonds (45-degree squares, vertex radius scaled by `PIN_DIAMOND_SCALE` so both shapes read the same visual weight), and an unconstrained match-type input that accepts either cardinality uses an axis-aligned square with a tangent inscribed circle. Outputs never use the combined shape. FILL carries the data type: concrete slots are solid type colors, MultiType slots divide the body into colored wedges (list colors always peel to the element type - shape says list-ness, color says what data flows, so `list<union<...>>` is a segmented diamond). OPTIONALITY punches out the center. IDENTITY marks Any/wildcard with a neutral gray fill and a thin dashed outer ring, while a match variable displays its identity such as `T`. Fixed and match pins use the same dark outer border. When graph inference resolves a match variable, its pin adopts the ordinary definite circle or diamond and concrete color. The first MultiType divider sits perpendicular to the node border, pointing at the noodle side (west for inputs on the left border, east for outputs on the right), so the split reads as a deliberate seam at any member count; wedges and dividers clip to the pin outline so one fill implementation covers every shape. Because the axes are orthogonal, an optional Any input keeps the dashed ring and hollow center without resembling a MultiType pie, and an optional list MultiType is a segmented diamond with a punched center. The visual-regression contract for this whole language is the gallery fixture pair (`e2e/fixtures/gallery-schemas.json` + `gallery-workflow.json`, exercised by `e2e/tests/gallery.spec.ts`), which instantiates every widget kind and socket variant in one workflow and screenshots it. See [Match types and lists](./match-types-and-lists.md) for user-facing behavior.
- Subgraphs as a sound abstraction: anything that works on a node works on a subgraph, including dynamic types.
- Get/Set ("named links") as a native graph primitive: real topology, optionally hidden, scoped to one graph (never crossing subgraph boundaries).
- Correct multi-tab execution tracking: progress never bleeds onto the wrong tab.
- "Frozen" execution views: the exact workflow that was submitted is always inspectable, with an in-sync/diverged badge.
- App-mode-ready: document elements have stable identities so alternate views can reference them later.
- Modular and extensible WITHOUT dirty hacks: a deliberate, versioned extension API (widgets, panels, commands, importers) with typed registration points. Core internals are not reachable, so monkey-patching is impossible by construction, not by policy.
- One workflow format: ID-keyed values (no positional widgets_values), the API prompt demoted to compiler output. Old formats translated on import, never dual-supported. Versioned and migratable.
- Node representation as a design system: any declared order of inputs/widgets/outputs, schema-driven sections/collapsing, no widget-vs-output line collisions, dynamic outputs anticipated.
- Live previews (images, animation, video, audio) as a built-in channel, so packs like VideoHelperSuite need zero special hacks.

## Non-goals (explicit)

- No backward compatibility with the LEGACY extension surface (litegraph monkey-patching, app.registerExtension, litegraph widget objects). Extensibility is a goal; compatibility with the old extension mechanism is not.
- No litegraph. No compatibility shims with the current frontend's object model.
- App mode itself is deferred; only the identity/binding foundation is built now.
- Import of existing workflow JSON is one-way (read old, write new format only).

## What the research established

### Backend (ComfyUI)

- Node definitions arrive via `/object_info` in the legacy V1 shape; V3 features are encoded as reserved type strings: `COMFY_MATCHTYPE_V3`, `COMFY_AUTOGROW_V3`, `COMFY_DYNAMICCOMBO_V3`, `COMFY_DYNAMICSLOT_V3`, comma-separated unions ("IMAGE,MASK"), `"*"` wildcard, `remote` combo fetch specs, `lazy`, `rawLink`, hidden inputs. (`comfy_api/latest/_io.py`)
- The prompt wire format is a flat `{node_id: {class_type, inputs}}` map; links are `["src_node_id", output_index]`. `partial_execution_targets` selects output nodes.
- Server type compatibility (`comfy_execution/validation.py`): exact match, `"*"` matches anything, comma unions pass on overlap, MatchType resolution is explicitly deferred to the frontend.
- WS protocol: `status`, `execution_start`, `execution_cached`, `executing`, `executed`, `execution_success`, `execution_error`, `execution_interrupted`, `progress`, `progress_state`, binary preview frames (types 1/3/4). Almost all execution events are routed ONLY to the submitting `client_id` and are keyed by `prompt_id`. `progress_state` carries `display_node_id` / `real_node_id` / `parent_node_id` per node.
- `/history` stores the prompt plus `extra_data`; embedding the workflow snapshot in `extra_data.extra_pnginfo` is how workflows are recoverable later.

### Current frontend (why not to copy it)

- ~6 layers between graph data and pixels; the same graph exists simultaneously as litegraph OOP objects, serialized JSON, Vue reactive mirrors (`VueNodeData`), Pinia stores, and a Yjs layout store. Complexity is concentrated in keeping these in sync.
- Dynamic typing is callback-driven slot mutation (`onConnectionsChange` handlers that rewrite slot types and disconnect links), which is exactly why it breaks at subgraph boundaries (`src/core/graph/subgraph-dynamic-input-limitations.md`: matchtype/autogrow do not work across boundaries; a boundary slot that first captures `"*"` permanently accepts anything).
- Execution progress projection resolves execution node IDs against "the currently loaded graph", which is the source of the wrong-tab progress bugs (`executionStore.ts` + `GraphCanvas.vue` progress watcher).

### Get/Set prior art (KJNodes)

- Frontend-only virtual nodes; name stored in a widget; type copied from the connected producer and propagated manually; resolved to real links at prompt-build time; the "hidden noodle" is manual canvas drawing, not topology; crossing subgraph boundaries required monkey-patching prompt-flattening internals. Every pain point comes from living outside the graph model.

### 1. Document model: one authoritative, plain-data source of truth

The workflow document is plain data (no behavior classes, no rendering fields mixed in):

- `GraphDefinition`: nodes, links, named nets, groups, reroutes, boundary ports, promoted parameters. The root workflow is itself a GraphDefinition; subgraph definitions are siblings in a `definitions` map keyed by UUID.
- `Node`: stable UUID, node class ref, values (widget state), dynamic-port materialization state, position/size, flags (collapsed, bypassed, muted).
- `Link`: source endpoint -> target endpoint. Endpoints reference (nodeId, portId), never slot indexes.
- `SubgraphInstance`: a node whose class is a definition reference.

Updates go through **commands/transactions** (add node, connect, set value, promote widget...), implemented with persistent/structural-sharing updates (Immer-style) producing forward+inverse patches. Undo/redo replays patches. A cheap structural validator runs after every committed transaction (no dangling endpoints, one incoming link per input, no cross-definition references, no recursive definitions, named nets stay in-definition).

Three distinct identities, never conflated:

- **Workflow lineage ID**: stable across saves/renames; identifies "the same workflow".
- **Document revision**: ephemeral monotonic counter for derived-state invalidation within a session.
- **Content hash + execution-semantic hash**: the semantic hash covers only compiler-relevant state (topology, values, classes), not layout/labels/view state. This is what "in sync with execution" compares.

### 2. Schema registry: normalize /object_info once

Raw `/object_info` is parsed once into a normalized, tagged schema model; no other subsystem touches the raw shape. Its core is an **ordered list of interface items** - not the legacy required/optional/widget buckets. V3 declares inputs as a list, so declared order is preserved verbatim; connections and widgets may interleave freely ("any order of inputs/widgets" is the default, not a special case). V1 definitions get a canonical order synthesized (required, optional, widgets) purely as an import convention - and the V1 path is a **quarantined adapter module designed for deletion**: NodeSchema semantics are defined against V3, nothing downstream knows V1 existed, and when the backend retires V1 (see section 18) the adapter is removed without touching anything else. Items express:

- ports with `PortType = concrete atom-set | any | variable(templateId, allowedAtoms)`
- variadic families (Autogrow: prefix or name-list, min/max) - **modeled symmetrically for inputs AND outputs**. Schema wire 26 ships count-bound top-level output families, and the representation, identity scheme, solver, compiler, and subgraph boundary projection handle their materialized members. Runtime-computed arity remains a separate unsupported contract.
- stored output descriptors (schema wire 39): a required string input declares ordered stable output IDs, names, and concrete type choices. Expressions and entry lists determine their interface before execution; model profiles bind it to a revisioned metadata probe and a canonical BLAKE3 asset digest.
- conditional groups (DynamicCombo options -> nested input sets; DynamicSlot -> nested inputs revealed on connect)
- widget specs (INT/FLOAT/STRING/BOOLEAN/COMBO/MultiCombo + the specialized widgets: color, curve, bbox, webcam, image compare...). Presentation hints in node defs (`multiline`, `display: slider/number/...`) normalize to a **default view id**, not distinct widget types - one value kind, many switchable views (section 10)
- value controller declarations (`control_after_generate` and kin) normalize to a **controller slot** on the widget spec - structured companion state, never a phantom extra widget (section 10)
- remote combo sources (route, refresh, TTL), upload flags, lazy/hidden/advanced/force-input flags
- node metadata (category, description, deprecated, experimental, output node, intermediate output)
- **presentation constructs**: named sections (collapsible or not), separators, and layout hints. These are pure presentation - typing, elaboration semantics, and compilation ignore them entirely - which is exactly why they "just work" with dynamic members: a section is a container of item references, and if an Autogrow family inside a section grows, the section simply contains more items. Sections are not semantically bound to the input/output divide; a section may reference outputs too, so a future backend change to group across that boundary is a schema addition, not a redesign.

Unknown constructs produce an explicit **unsupported-node** state (rendered as an inert node with raw config preserved), never guessed behavior. The raw def is retained for diagnostics.

**The critical property: this normalized NodeSchema is the ONLY interface description in the whole system.** Backend nodes normalize into it, and subgraph definitions *derive* one from their boundary (section 4). Everything downstream - elaboration, type solving, rendering, promotion, compilation, app-mode bindings - consumes NodeSchema and never asks "is this a real node or a subgraph?". That is what makes "anything that works on a node works on a subgraph" true by construction instead of by bug-fixing.

**Deprecation + replacement: declarative rules, executed as commands.** The backend today has only an `is_deprecated` flag; the frontend's replacement handling is scattered and buggy. Here it is a schema-level contract:

- A deprecated NodeSchema may declare a **ReplacementRule**: target node type (+ minimum schema version) plus a declarative mapping for every target input/widget/output. Mapping sources: copy from a source port/widget by semantic ID, constant, or a transform from a small closed vocabulary (enum-option rename, numeric scale, merge/split of widgets). Output mappings preserve downstream links, type-checked by the solver.
- **One-to-many replacement is additive.** A case may declare helper `nodes` keyed by structural local ids and acyclic internal `links`. Case-local string addresses use `port` for the primary target and `localId:port` for a helper; `inputs` and `outputs` accept those addresses while MappingSource and source-output semantics remain unchanged. The primary keeps the source node id. Helper document ids are deterministic (`sourceId:localId`), collisions are plan errors and apply-time stale-plan errors, and created-node plan rows retain local-id provenance. A boundary binding that would move to a helper fails with `replace.boundary.helper`; v1 never silently retargets a boundary to another node. Helpers are not re-planned in the same scan/apply pass. The planner remains geometry-blind; apply places helpers in declaration order in a column 320px right of the primary, spaced 180px vertically (primary fallback position `(0, 0)`). Cases without `nodes` or `links` produce the byte-identical one-to-one plan shape. If a later primary-chain hop would reference an allocator-created internal link from an earlier hop, the scan stops with `replace.chain.createdLink`; apply the reviewable prefix and rescan. Supporting that combination in one shared-actor batch requires stable plan-local link handles and is explicitly deferred in `promises.md`.
- **Conditionals are guard lists**, evaluated top-down: each case has a condition over the source occurrence's elaborated state - input connected/absent, widget value present, value equals X, port exists - and the first matching case wins, with a required fallback. "If an input is missing do X, otherwise Y" is exactly one guard pair. Conditions are a closed, serializable predicate set - not code - so rules are testable against a golden corpus (old instance -> expected new instance) and safe to ship as schema data.
- **Application is an ordinary document command**: atomic, undoable, operating on elaborated interfaces. Ambiguous or impossible mappings produce diagnostics and leave the node untouched - never silent guessing (the current system's failure mode). **Auto-apply is the default (decided)**: clean, diagnostic-free mappings apply on load without ceremony (undoable, and recorded as a load diagnostic so it is visible after the fact); a settings toggle switches to review mode - a refactor-style per-node preview with batch apply - which doubles as the debugging path for rule authors. Mappings that raise diagnostics always drop to review regardless of the toggle. Applies across subgraph definitions too (instances update via rederived boundaries).
- **Rule sources are layered**: the successor schema itself (self-describing), pack-shipped rule files, and a core-maintained table for historical renames. Rules are versioned under the format's additive-first policy. The escape hatch for genuinely complex migrations is a programmatic migrator registered through the extension API - it still runs inside the command layer with the same diagnostics, so even the escape hatch cannot mutate the graph outside a transaction.
- **Composes with what exists**: the legacy importer can auto-apply rules (with review diagnostics); missing-node placeholders preserve identity + values byte-for-byte, so a replacement rule targeting that identity can upgrade a placeholder even when the original pack was never installed; deprecation badges render via the standard node-badge registry.
- **Search visibility is a separate axis from validity (decided).** A schema may declare `searchVisibility: 'normal' | 'deprecated' | 'hidden'`: deprecated nodes list in the palette with a badge and rank below normal results; hidden nodes never appear in search but remain FULLY valid in existing workflows - the "old node keeps a genuinely unique behavior, deprecated but not invalidated" case, without the legacy hide-and-rename contortions. Display-name reuse is safe by construction: identity is the type id everywhere (values, links, rules, provenance); displayName is pure presentation, so a successor may carry the same name as its hidden predecessor. The palette's one rule: never list two same-named entries when one is hidden.
- **Structured deprecation messaging + in-place replace (decided, shipped both sides).** The boolean `deprecated` extends additively to `deprecation: { message, since?, replacement? }`. The deprecation badge is interactive per the badge/popover contract: it shows the author's message ("going away soon, use X because Y") and, when a ReplacementRule targets this type, a "Replace in place" action dispatching the same atomic command the review UX uses. Workflow load surfaces the scan summary ("3 deprecated nodes, 2 auto-upgradable") through the ordinary diagnostics channel. The Dinkster schema wire (v3, additive) now carries all three fields - `deprecation`, `searchVisibility`, and `"replacements": [rule, ...]` mirroring our ReplacementRule vocabulary field-for-field; all are excluded from the backend's schema signature so shipping migration advice never invalidates caches. The frontend soft-demotes deprecated schemas in search when `searchVisibility` is omitted (the backend never auto-demotes; the inference is deliberately ours).
- **Chains resolve on both axes (decided).** Deprecations and replacements compose: A's successor B may itself be deprecated/replaced by C. The two chains are DIFFERENT mechanisms and never conflated:
  - `deprecation.replacement` pointer chains are name-only display data. The UI resolves them transitively (`resolveDeprecationPointer`) and steers to the TERMINAL type; cycles, dangling targets (packs load independently), and runaway depth degrade to explicit statuses, never loops or silence. A pointer is never reinterpreted as an executable migration.
  - Replacement-rule chains are executable and SEQUENTIAL: a hop can transform values and move links, so A -> C is never shortcut. The scan plans hop N against the document state hop N-1 produces (scratch-applied through the real `node.replace` command, so staleness guards hold by construction). A scan item is the whole chain: `hops`, `terminalType`, and a status - `terminal` (settled), `blocked` (a later hop failed to plan; the safe prefix survives for review), `cycle`, or `depth` (bounded by `REPLACEMENT_CHAIN_LIMIT`). `safe` - the auto-apply gate - requires a terminal chain with EVERY hop warning-free; one warned or missing hop drops the whole item to review. Applying dispatches every hop of every item in one batch = one revision, one undo step, all-or-nothing (the batch command runs sub-invocations against the transaction's working copy, so later hops see earlier type changes).

### 3. Two-stage derived state: interface elaboration, then type solving

This is the core correction over the current frontend, which conflates "what ports does this node have" with "what types are they" and mutates both via callbacks.

**Native output identity.** Dinkster supports count-bound output families: a stored
literal count determines canonical members such as `images.0`, `images.1`.
Linked counts are refused rather than guessed. The compiler records `outputIds`
on each prompt node in exact wireable elaborated order, excluding ghost ports
and using the same backend-ID and region-alias mapping as direct native region
lowering. Native submission indexes this list, not the raw catalog, so effective
outputs absent from the catalog and differing catalog order cannot retarget a
link. Malformed lists and out-of-range indexes fail closed; legacy prompts
without the list retain catalog/output-family conversion. These IDs remain in
frozen and persisted execution proofs and participate in recipe equality;
older proofs without them do not establish exactness against new compiles.
The ComfyUI V1 adapter strips this compiler-only field before submission.

**Stored heterogeneous interfaces.** Descriptor sources remain ordinary saved
string values, not a parallel graph schema or runtime-generated topology.
Elaboration projects their ordered entries into normal typed outputs; labels
and order can change without retargeting stable IDs. Subgraph boundaries
project source literals and metadata-probe asset inputs per occurrence,
including chained forwarding and definition defaults. Linked schema sources
remain invalid rather than guessing an interface. The editor commits one
ordinary undoable value command; probed entries are read-only and replaced by
a current probe result. Connection, occurrence, asset, and revision checks
discard stale responses. Backend admission revalidates metadata before cache
lookup, and workers independently compare the effective interface. See
[dynamic outputs](dynamic-output-families.md) for the authoring contract.

**Stage 1 - interface elaboration** (per node, from schema + stored values + connection state): produces the node's *effective interface* - the concrete, ordered set of input AND output ports that exist right now. Autogrow members, active DynamicCombo branch inputs, revealed DynamicSlot inputs, and count-bound variadic output members all elaborate through the same code path. Every dynamic port gets a **persistent identity** (stored UUID per variadic member, semantic path for conditional inputs) so links, undo patches, and view bindings survive membership changes; API input names and output indexes are compiler output, not identity. Explicit transition policies: switching a DynamicCombo branch preserves branch-local values; disconnecting a DynamicSlot hides (not deletes) nested ports; autogrow keeps one trailing empty member. An Autogrow template is a **list of slots** and one member is one stamped group instance: connecting or assigning ANY slot of the trailing ghost promotes the whole group, and hiding never deletes state. Stamped ports are addressed `<family>.<slotId>` + member id uniformly - even single-slot templates - so a schema growing its template into a group never reshapes existing document addresses; grouped wire names (`items.item0.image`) are a provisional compiler derivation pending backend group naming, never identity. Template slots may themselves be dynamic constructs - conditional constructs AND nested Autogrow families (custom packs invent their own dynamic schemes; the system is designed to absorb them rather than force hacks). The identity model generalizes once: **a port's member identity is a path** (`members: DynamicMemberId[]`, one stable generated id per family crossed, outermost first) alongside the dotted slot path, and per-member nested state lives in canonical member-keyed metadata (`members` list stays the sole ordering source; a `memberState[id].dynamic` map carries inner family/choice state - never array-indexed, never a second representation). Packed keys (`items.sub#m0#g0`) are opaque, injective, address-derived value/map keys - stable ids, not ordinals, so member reordering never moves a value; nothing ever parses a stored key back apart. Ghost policy: at most one ghost ancestor on any rendered address - inside a ghost member, nested families elaborate their minimum with NO nested ghost, and ghost-subtree ports never compile (enforced centrally by scoped emission, not per handler). Interacting with any port in a ghost subtree is an **atomic materialize-and-write command**: materialize implicit ancestors, promote the one ghost ancestor, write the link/value/selection - one transaction, one undo step; a committed document never references unmaterialized members (violations are load diagnostics, never elaboration-time mutation). Elaboration state lookup is a scope-local cursor (entering a member hands the child scope that member's nested state as its root), and elaborated ancestry (member path, ghost flag) is orthogonal to the leaf role. Hard parser/elaborator budgets (depth AND total items/ports) fail deterministically instead of warning after exponential work. Invariants N1-N6 in hazards.md.

**Stage 2 - type constraint solving** over the elaborated topology. Not naive whole-graph unification - a constraint system that respects backend semantics:

- `"*"` imposes NO constraint (it is not a type variable).
- Concrete unions check by atom-set overlap per link; a producer declared `IMAGE,LATENT` can feed an IMAGE consumer and a LATENT consumer simultaneously without being forced to one atom.
- MatchType templates are real variables, freshened **per node occurrence**; equality constraints tie occurrences within one node (and across a subgraph boundary when the boundary port is declared generic). Allowed-type domains constrain variables. A required closed DynamicSlot may bind one such variable from its stored selected variant, including variables nested under list/asset constructors; this authoritative constraint resolves matching outputs even before any edge is connected.
- Results per variable: unconstrained (no concrete edge or stored slot selection constrains it - render the declared expression), resolved atom, valid-but-ambiguous (render as the remaining union), or conflict. Conflict blame is deterministic and complete: EVERY edge that contributed to the class is marked invalid (never "whichever link came last"), with one diagnostic per class - links are marked, never auto-disconnected.

Solved types are derived state: recomputed (incrementally, dirty-region) on topology change, rendered from, but never written back into the document or schema. Conformance fixtures are generated against `comfy_execution/validation.py` rules so frontend and server agree on compatibility.

**Why this pipeline cannot oscillate** (the old frontend's callback cascades are the cautionary tale): elaboration inputs are restricted by construction to (schema, stored values, link *existence*). Autogrow depends on materialized members, DynamicCombo on a widget value, DynamicSlot on connectedness - none depend on solved types. So the dependency structure is a DAG: `document -> elaboration -> solving -> rendering`, evaluated innermost-definition-first and memoized per definition. There is no feedback edge from solving into elaboration, hence no fixpoint iteration, no ordering sensitivity, and no "connect A then B behaves differently than B then A" class of bugs. Any future feature that would need type-dependent elaboration must be rejected or given an explicit, documented stratification - this invariant is load-bearing.

**Type-driven specialization (DynamicSlot and kin) is a materialized choice.** A schema may declare that a slot specializes on the connected type (per-type nested input sets, per-type widget specs). The mechanism: connecting is a command, and the interaction layer - which may legitimately read solved types for UI decisions - writes the selected variant into the node's **persisted dynamic state**, exactly like a DynamicCombo selection set by a gesture instead of a keystroke. Elaboration keeps its restricted inputs, so the no-feedback DAG holds by construction, and the choice is serialized (exact reproduction), deterministic on load, undo-friendly, and user-overridable like any value. A required closed slot may additionally bind its selected concrete variant type to a MatchType variable shared by outputs. The stored choice remains the sole authority: solving substitutes it through the active interface, but solved graph types never choose or rewrite the variant. If the upstream type later changes, the stored choice goes stale like any other mismatch: the advisory solver marks it, nothing auto-deletes, and re-picking (manually or via a repair command) resolves it. When the connected type is generic/unresolved at connect time, no variant is auto-selected - the slot stays in its unspecialized base form until the type is known at a later gesture or the user picks. The alternative - elaboration reading the *declared* type of the linked producer's port - was considered and rejected: it makes one node's elaboration read another node's elaborated ports (cycle risk once producer ports are themselves dynamic) and still cannot specialize on generic producers (hazard T1).

### 4. Subgraphs: definitions as polymorphic type schemes

- `SubgraphDefinition` = GraphDefinition + declared boundary ports + promoted parameter bindings (references to inner (nodeId, portOrWidgetId)).
- Boundary ports may be concrete or generic (a MatchType-style variable). A definition behaves as a **type scheme**: every instance freshens all boundary and internal variables, so one definition can resolve to IMAGE in instance A and LATENT in instance B. The definition is never mutated by an instance's resolution - this is the invariant the current frontend violates and why its `"*"` boundaries "freeze".
- Instances reference definitions by UUID. Editing a definition invalidates derived state for every occurrence; boundary deletions leave dangling instance links as visible diagnostics, never silent deletion.
- Occurrence identity is a path: `{instancePath: SubgraphInstanceId[], localNodeId}`. Compiler provenance, execution projection, diagnostics, and (later) app-mode bindings all use qualified occurrences, since one definition node exists once per instance.
- Recursive definitions are prohibited (validator-enforced).
- **A subgraph's public interface IS a NodeSchema.** The boundary declaration compiles into the exact same normalized schema representation backend nodes use - including, in the full design, type variables (generic ports), variadic families (a boundary group forwarding to an inner Autogrow port), and conditional groups. Instances are elaborated and type-solved by the same code paths as any node; nothing downstream distinguishes them. This is the anti-cornering guarantee: dynamic-type support for subgraphs is not a special case that accumulates bug fixes - it is literally the same mechanism.
- **Family forwarding, including split forwarding (designed; lands with compile integration).** A boundary item may forward a whole inner dynamic family; the derived schema carries the family spec (types freshened per inner node) and each instance persists its OWN member list - the definition is never written by instance interactions. Split forwarding is supported with one pinned rule: definition-local members form a fixed prefix, instance members append as the suffix (recursively for nested forwarding, innermost definition first). Member state never merges in the document - the flattener synthesizes a per-occurrence merged member list and feeds the ordinary elaboration path; derive-boundary bakes the adjusted capacity (min/max minus prefix count) and label/ordinal offset into the derived spec. Renumbering on definition edits is correct and harmless because identity is the member id, never the ordinal. This composes with member-wise binds (a bound prefix member fed by a static boundary input = "named first slot + growable rest"), group templates, MatchType (all members constrain the same per-occurrence variable), and dynamic outputs. **Slot-selective forwarding** (`binds.slots`) additionally lets a grouped family expose only a subset of its template slots at the boundary: entries are dotted paths ('sub' exposes a slot or whole nested subtree, 'sub.s' narrows a nested autogrow to listed descendants with ancestor exposure implied), the derived template is filtered (template order, recursively), member identity/capacity/ordinals are untouched, unexposed widget slots compile template defaults, and unexposing a required socket-only slot reachable by appended members - including inside a narrowed nested construct, regardless of its min - is a derive-time error. Removing the selection ("unsplitting") restores the full template without rewriting anything. Invariants F1-F10 in hazards.md.
- **Boundary input fan-out (`alsoBinds`)**: one boundary input may drive MANY inner inputs. The primary `binds` stays authoritative for the derived type, widget promotion, and display; `alsoBinds` is an optional, input-side-only list of additional `'port'` targets that receive the same outer edge or promoted value (the compiler lowers one delivery per target; a muted/bypassed target drops out without killing the live ones). Outputs keep exactly one source, and whole-family forwarding stays singular through `FamilyCrossing` - fan-out entries must be concrete port routes (dynamic member routes included). Satisfiable-without-a-connection is the conjunction over all targets; an additional target that does not accept the primary's type is an advisory warning (`boundary.fanoutTypeMismatch`), never a load failure. Edited via the undoable `boundary.addBinding`/`boundary.removeBinding` commands; node removal prunes only the affected route (removing the primary's node drops the item). This mirrors backend regions, where any number of body links may read the same `$region` port.
- **Boundary spec refinement**: a boundary port / promoted parameter may carry an optional declared partial widget spec (min/max/step/precision, options...) that **narrows** the inner input's constraints - the subgraph author's "rules for this value". It serializes with the definition, flows into the derived NodeSchema, and is therefore seen identically by the graph view, value sources feeding the instance, and later app-mode bindings. A refinement that widens or contradicts the inner constraint is a boundary diagnostic. (Replaces the legacy frontend's hidden PrimitiveInt/Float property-proxy hack with a declared, serialized field.)
- **Unsync is one cheap command.** Instances share a definition by reference (copying an instance copies the reference - synced by construction), and **detach** is the first-class inverse: one undoable command that clones the definition and repoints the instance at the clone, preserving connections, promoted values, position, and view state. Surfaced wherever the sync question arises: on the instance (context menu/badge showing "1 of N instances"), and as a guard on definition editing - entering edit mode on a multi-instance definition offers "edit all N instances" vs "detach and edit this copy". **Retention amendment (2026-07-29):** definitions with no remaining instances are retained on save. No persisted provenance distinguishes a reusable orphan from a detached clone, and automatic garbage collection risks silent data loss under undo/collaboration. Deletion is an explicit future command with dependency preview, as specified by `docs/subgraph-lifecycle-design.md`.
- **Phased exposure, not phased representation.** The boundary -> NodeSchema derivation (including variadic/conditional constructs) is specified in the initial contracts and baked into the file format and port-identity scheme from day one. The v1 *UI* exposes concrete and generic (type-variable) boundary ports with fixed arity; variadic/conditional boundary groups are switched on in a follow-up. Enabling them later is purely additive - no migration, no frozen-boundary bugs, no re-architecture. Never ship a boundary feature whose identity/serialization story is not already in the format.

### 5. Named nets: get/set as first-class topology

Modeled as a **named net** (hyperedge), not virtual nodes and not a name attribute sprinkled on unrelated links:

```ts
interface NamedNet {
  id: NamedNetId
  name: string            // unique per graph definition (case-insensitive)
  source: OutputEndpoint | null   // exactly one writer
  sinks: InputEndpoint[]          // many readers
}
```

- Scoped to one GraphDefinition by construction - cannot cross subgraph boundaries, so definitions stay portable between workflows (the user's requirement). Sibling/nested graphs can reuse names freely.
- Type-checked exactly like normal fan-out by the constraint solver; type is inferred from the source, sinks constrain it.
- Compiled by lowering each sink to a direct source->input link; the net itself never reaches the server.
- Rendering keeps one authorable Set view at the source and one Get view at each sink. The views are selectable, movable, and deletable; deleting a Get disconnects that sink, while deleting the Set removes the net through the existing commands. Full noodles remain the default and can be collapsed independently of the endpoint views.
- Collapse is strictly visual. A collapsed net's deliveries stay in the scene as hidden links: painting, hit testing, visual bounds, and the minimap skip them, but every connectivity consumer (connected-pin styling, driven-widget suppression, pin reveal, occupancy, gestures) sees them, so a net-sink input presents exactly like a link-driven input whether the noodle is shown or not.
- Endpoint drags carry the net, collapsed or expanded. Dragging a net-driven input to another input moves that sink's membership (`net.connectInput` + `net.disconnectInput` in one batch); dragging it to a reroute or selector detaches the sink and connects an ordinary link from the net's source; a moved empty drop detaches the sink. Shift-dragging the source fan-out re-points the whole net via `net.setSource` (batched with `link.rewireSource` when ordinary links share the pin); because a net's source must be a real node output, a fan-out carrying net membership refuses reroute, value-source, selector, and widget-tap drops, and an empty drop leaves nets attached.
- Get/Set positions are advisory presentation state in `doc.ext['dinkster.netViews']`, keyed by graph definition, net, role, and sink endpoint. A manually placed tag stores an `offset` from its owning node's top-left (source role: the net's source node; sink role: the sink endpoint's node), so the tag follows the node through drags, paste, subgraph extract/flatten, and occurrence localize while keeping the user-chosen offset. Disconnecting a sink removes its authored Get entry in the same transaction, and removing a net removes all of its authored entries, so undo restores topology and presentation state together. The retired `position` form (absolute world coordinates) is canonicalized to an equivalent offset on load whenever the owning node has a stored view position - the tag renders at exactly the same point, so nothing jumps - and survives as-is (rendering where it was saved, not following) only when the owner cannot be resolved. An entry carrying both forms is malformed. Malformed or foreign entries do not prevent loading and remain byte-for-byte JSON-equivalent unless that exact view is moved or its owning sink or net is removed. All occurrences of a definition therefore share its view geometry without changing occurrence-local runtime identity.
- Editing affordances: create from an output ("publish as..."), attach from an input picker filtered by type compatibility, rename propagates net-wide (it is one entity, so rename is trivial - no KJNodes-style name-string chasing). Source-less nets are legal while editing but a compile diagnostic. Creation, connection, disconnection, rename, and removal continue to use the `net.*` command family; the views introduce no document node or compile representation.
- Copy/paste collision policy: pasted net with an existing name merges as additional sinks if types agree, else auto-renames (`name_2`).

### 5b. Value sources: primitives as declared literals

The legacy frontend PrimitiveNode is the archetype of everything section 6 bans: a virtual node with a `*` output that mutates its own type/widget from whatever it touches first, and smuggles its value into real nodes by write-through widget mutation at queue time (`applyToGraph`). Its replacement is a **value source**: the fourth member of the closed structural-construct set (reroutes, named nets, selectors, value sources) - real topology, one output, fan-out to many inputs, compiled away deterministically.

Note the backend now ships real primitive nodes (PrimitiveInt/Float/String/Boolean) - those are ordinary compute nodes needing zero frontend support. The value source exists for what they cannot cover: consumer-defined widget config (COMBO option lists, custom widget kinds) and compile-time literal baking.

- **The document stores: value, optional declared spec, controller state, position/view.** Nothing else. The declared spec is a serialized partial widget spec (kind, min/max/step/precision, options, controller slot...) and is **authoritative**: declared fields are taken as-is.
- **Derivation only fills undeclared fields.** The constraint solver (NOT elaboration - the no-type-feedback DAG invariant holds) unifies the connected consumers' input specs and fills whatever the user left unspecified. A fully-declared source is static: the solver only checks compatibility. A "pin current spec" command converts derived -> declared in one step, so if derivation ever proves to be a minefield it can be narrowed or removed **without breaking any saved workflow** - the dynamic part is a convenience, never load-bearing (the exact inverse of the legacy design, where dynamic adoption WAS the serialization story).
- **Conflicts are diagnostics, never mutations.** Constraint merging is per-kind and deterministic (range intersection, option-list intersection), defined by the WidgetKind contract. An empty merge, or a declared spec incompatible with a consumer, is a link/source diagnostic. There is no "first connection wins" and no spec stored from a connection event.
- **The value is never hostage to the spec** - the same policy as remote combos (section 10). Disconnected source, conflicting consumers, value outside current options: raw-value fallback view + diagnostic, never a value reset, never widget deletion.
- **The compiler bakes the value into each consumer's input** in the prompt and records it in the CompileArtifact. No write-through into consumer widgets, ever. Frozen views, semantic hashing, and scope-aware controller advance behave correctly for free.
- **Controller slots compose**: controller state (fixed/increment/decrement/randomize) lives ID-keyed on the source and advances only when at least one consumer is in the executed closure - the partial-execution rule applies unchanged.
- **No special cases downstream**: a value source feeding a subgraph instance input reads that instance's derived NodeSchema like any consumer; feeding a named net composes as plain topology ("graph variable with a literal"). Any registered WidgetKind works automatically because spec derivation is kind-agnostic.

### 5c. Widget taps: any widget as a producer (implemented)

The old ecosystem's "widget as output" requests dead-ended because node definitions and the prompt format were fixed server-side. Here the prompt is compiler output, so the feature needs zero backend or schema changes. A **widget tap** is a new link *producer endpoint kind* - `(node, inputId)` - alongside port/reroute/value-source endpoints; NOT a fifth structural construct (it introduces no topology entity of its own, just edges).

- **Semantics: "the value this node will execute with."** If the tapped input holds a literal, the compiler bakes the *effective* value (instance-promotion overrides included, per occurrence - the value-source baking path, reused). If the tapped input is itself link-driven, the tap **aliases the incoming link**: consumers get exactly the producer the node itself consumes. Both lower deterministically and are recorded in the CompileArtifact.
- **Type** is the tapped input's declared concrete type; combo values are strings (remote combos included - the value is the chosen string, section 10's value-never-hostage rule applies). Taps on non-concrete inputs are a document diagnostic.
- **Non-concrete destinations** (wildcard/union/variable inputs, e.g. PreviewAny): an undriven tap's literal lowers to the reserved `{"$typed": {type, value}}` graph wire marker stamping the tapped input's concrete type, gated on the backend advertising `typedLiteral` in `/api/nodes` `dinkster.graphFeatures` (joint contract, Dinkster ea6eca7). Concrete destinations always keep the canonical plain literal (emission rule); without the capability the compile refuses loudly with `compile.tap.nonConcreteTarget` instead of bouncing off the server. Value sources declare no runtime type, so a value-source bake into a non-concrete input refuses even with the capability. Capability plumbing has two invariants: queue compiles and would-run scope previews share ONE input builder (`AppState.compileInputForTab`) so they can never disagree on `graphFeatures`, and a backend reconnect invalidates held capabilities unconditionally (a restarted server can change `graphFeatures` at an equal or lower schema epoch, so the epoch gate alone must not swallow the refetch).
- **Format**: additive LinkEndpoint variant. Tap edges participate in cycle validation like any edge (a tap that aliases a link contributes the aliased edge's dependency, so alias cycles are caught by the same pass).
- **Rendering**: a tap pin on the widget row's right edge, revealed on hover/drag-over and when connected - a row affordance within the section-12 design system (which already guarantees no widget-vs-output line collisions), never always-on pin clutter.
- **Relation to value sources**: value sources remain the standalone declared-literal construct with fan-out; a tap turns an *existing* node's widget into the source without restructuring. The two compose (a value source feeding an input that is then tapped aliases through).
- **Subgraph boundaries**: a tap on a promoted boundary widget reads the derived NodeSchema input like any consumer; taps forward through flattening per occurrence with the same machinery as value-source baking. No definition-level special case.

### 6. Graph control: mode flags, control surfaces, and selectors

rgthree's Fast Muter/Bypasser, Fast Groups Muter, Node Mode Relay/Repeater, and Random Unmuter prove real demand for controlling the graph (mute/bypass, group toggles, randomized branch selection) without server involvement. Their current embodiment is everything this architecture bans: virtual nodes with `*` control links masquerading as dataflow, group targeting by re-scanning geometry every 500ms, procedural `node.mode` assignment with no command boundaries (bulk toggles are not atomic undo steps), a monkey-patched mode setter, and Random Unmuter temporarily mutating live graph state around the prompt-compile call. The demand decomposes onto three contracts this design already has - **no second category of "node" is needed**:

1. **Mute/bypass are document mode flags** on any node or subgraph instance, changed only through commands - so a bulk toggle is one atomic, undoable transaction, whoever initiates it. Compiler semantics are specified, not incidental: *bypass* lowers to a type-matched passthrough (same-slot-index preferred, then exact type match, using solved types - the current frontend's DTO heuristic, made deterministic and testable); *mute* drops the node's contribution and surfaces "required input now unsatisfied" as a **compile diagnostic before submit** instead of a server round-trip error. Subgraph instances mute/bypass at their boundary NodeSchema; flattening respects the flag - no recursive descendant-poking (rgthree needed a depth-first hack for exactly this).
2. **Control surfaces** are canvas-resident panels that are NOT nodes: no ports, no types, no presence in compilation. They hold stable **bindings** (node IDs, group IDs, tag/color queries) and **dispatch commands** (set mode, queue an ExecutionScope, run a macro). Fast Muter becomes a mode panel bound to picked nodes; Fast Groups Muter binds to a group ID with membership as subscribed derived state (no polling); Fast Actions Button is a macro panel over the command registry. They render with the same row/widget machinery, inherit undo for free because everything is a command, and are an extension point (register new surface types via the extension API). Constraints like "at most one active" are declared invariants on the surface, enforced in its command - not a UI-only convention that external changes silently violate.
3. **Selectors** join reroutes, named nets, and value sources (section 5b) in the existing third category, **structural constructs**: entities with real topology, type-solved like ordinary fan-in, compiled away deterministically. A selector picks one of N incoming branches - by widget value, or by policy including *random* - and the choice is resolved **at compile time and recorded in the CompileArtifact**, so a randomized run's frozen view shows exactly which branch executed (Random Unmuter's choice is invisible and unserialized). Unselected branches drop out of the prompt closure, the would-run highlight, and controller advancement - all for free, because they all derive from the same compile/scope machinery.

**Serialization (decided)**: control surfaces are part of the document and serialize in the workflow format - a shared workflow must arrive with its mode panels, bindings, and macros intact. They are, however, excluded from the **execution-semantic hash**: a surface never affects compilation (only the mode flags / selector values it *sets* do, and those are ordinary serialized document state), so adding/moving/rebinding a panel must not make a frozen view report divergence. Exact-result reproducibility is carried by the chain that already exists: mode flags and selector widget values serialize with the document, and the CompileArtifact snapshot records resolved random selector choices - so "what actually ran" is always recoverable even for randomized runs.

Why this avoids the two-category confusion: the old ecosystem's confusion came from control logic *pretending to be executable nodes*. The taxonomy here is explicit, small, and visually distinct - **compute nodes** (NodeSchema, compiled to the prompt), **structural constructs** (real topology, compiled away: reroutes, named nets, selectors, value sources - a closed core set), and **control surfaces** (no topology, commands only). Each has a distinct contract and design language; nothing masquerades. Relay/Repeater chains become largely unnecessary - they were wire-plumbing to fan out mode changes, which bindings, group targets, and command macros express directly; aggregate mode display ("all my targets muted?") is just a derived-state subscription on a control surface.

### 7. Compiler: CompileArtifact, not just a prompt

Compilation is a pure function `(document, schemaRegistry) -> CompileArtifact`:

```ts
interface CompileArtifact {
  documentSnapshot: WorkflowDocument      // immutable snapshot at submit time
  documentContentHash: string
  executionSemanticHash: string
  prompt: ApiPrompt                       // flat {id: {class_type, inputs}}
  flatToSource: Map<FlatNodeId, NodeOccurrence>
  sourceToFlat: Map<OccurrenceKey, FlatNodeId[]>
  diagnostics: CompileDiagnostic[]
  schemaFingerprint: string
}
```

Stages: structural validation -> interface elaboration -> type validation -> subgraph flattening (fresh flat IDs per occurrence; IDs are opaque, provenance lives in the maps - never parsed back out of ID strings) -> named-net + reroute lowering -> mode resolution (mute exclusion with diagnostics, typed bypass passthrough) + selector resolution (choice recorded in artifact) -> literal vs link serialization -> hidden/lazy/optional handling -> flat validation -> provenance emission.

The submitted `extra_data.extra_pnginfo` embeds a versioned workflow snapshot (as today) so PNG metadata and `/history` recovery keep working.

**Native graph wire with first-class regions.** The native Dinkster submit shape (`{nodes}` entries of `{nodeType, inputs}` OR `{region: {...}}` - map/fold/while with typed ports, element/state port roles, gather/state/flatten output modes, zip/cross/broadcast binding, nested body graphs reading ports through the reserved `$region` pseudo-node) is owned by ONE core module (`compile/dinkster-graph.ts`), same quarantine rule as the schema-wire decoder: types, the TypeExpr *encoder* (region ports put type expressions on the wire, refusing atoms-only violations the backend bans), and the admission validator. The validator covers shape, ports, state chains, dangling outputs, ids, cycles, gather/flatten runtime-resolvability, plain literals on non-concrete inputs, and schema selectors inside region bodies. Compile supplies occurrence-local elaborated types and selector facts; validation never derives producer types from literal stamps. Diagnostics retain the backend-compatible `/`-joined wire path (`r/add`) in data while their anchors point to the authored occurrence and port. A `lazy` input marker is not a selector marker and keeps its separate backend runtime behavior. Flatten concatenates list-typed body outputs in iteration order and preserves their `list<T>` type, including a typed empty list for zero iterations; it is legal for every region kind and never participates in state chaining. Broadcast iterates to the longest element list and repeats each shorter list's final element; map and fold accept it under their existing element-port rules, while rejects it like cross. Submit runs the wire-only part again after dynamic prompt expansion. Runtime iteration ids (`r[3]/node`) resolve through the existing runtime-path parser; regions are the backend's loop/conditional model (zero-or-one-element map = "run this subgraph, or don't").

For broadcast runtime cardinality, all element lists empty means zero iterations; mixed empty and non-empty lists fail loudly because there is no final element to repeat from an empty list.

### 8. Executions: first-class objects, snapshot-anchored

```diagram
+---------+  compile   +----------------+  POST /prompt   +--------+
| Document|----------> | CompileArtifact|---------------> | server |
+----+----+            +-------+--------+                 +---+----+
     | keeps editing           | owned by                     | WS events
     v                         v                              | (prompt_id)
+---------+            +----------------+ <-------------------+
| tab view|<--join by--| Execution      |
| overlay |  lineage + |  - artifact    |
+---------+  semantic  |  - status      |
             hash      |  - node states |
                       |  - outputs     |
                       +----------------+
```

- An `Execution` is created **before** the POST (so `execution_start` racing the HTTP response has a home); WS events with unknown `prompt_id` are buffered briefly until matched.
- Every event routes into the Execution by `prompt_id` - never "the active tab". Raw identities are preserved (`runtimeNodeId`, `displayNodeId`); display projection resolves `displayNodeId` through `flatToSource` to a qualified occurrence. Unknown node IDs (backend graph expansion) are kept, not dropped.
- **Tab overlays**: a tab shows an execution's live progress iff `workflowLineageId` matches AND `executionSemanticHash` equals the tab document's current semantic hash. Layout-only edits don't break the badge (semantic hash unchanged); semantic edits flip the state to "diverged".
- **Frozen views**: every Execution owns its snapshot, so "view executed workflow" opens the snapshot read-only in a tab - progress there is accurate by construction. UI: an executions rail/queue lists running+recent jobs; each shows a frozen/snowflake badge while the source tab is in sync, switching to a "diverged" indicator on the source tab once edited. One click opens the frozen view. "Restore this snapshot as editable copy" is the escape hatch.

**Partial execution is a first-class scope, not a checkbox.** The server accepts `partial_execution_targets` (a subset of output nodes; it schedules only them and their dependency closure). We model this as an **ExecutionScope**: a pure function of the document that yields the target set and its upstream closure. Everything derives from that one object:

- **Queueing**: the compiler receives the scope and emits `partial_execution_targets`; the CompileArtifact records the scope, so frozen views and history show what was actually requested.
- **Scope-aware compile diagnostics**: link lowering runs before closure construction because the staged producer references define the closure and structural failures must explain broken in-scope paths. Values and dynamic interfaces are also staged first because taps and dynamic ports affect lowering. Once the closure is known, node-owned diagnostics apply only to included nodes, so an invalid node on an unrelated branch neither blocks partial submission nor hides its partial actions. Invalid nodes within the closure still block. Full compilation keeps its historical behavior of validating every flattened node, including disconnected non-output nodes. Unowned structural topology diagnostics remain graph-wide. CanvasHost's live solver and widget-value diagnostics also remain graph-wide because they describe the editable document, not one queued artifact.
- **Would-run highlight**: selecting a partial-executable node (or arming a partial-queue action) highlights the closure - the same closure object the compiler will use, so the preview and the submission cannot disagree. Performance: the closure is an O(V+E) upstream traversal computed once per selection change (not per frame), memoized against the document revision, rendered as a scene overlay (dim excluded / outline included) - no per-node work in the render loop. After submit, `execution_cached` refines the picture: nodes the server skipped get a cached marker on the live overlay, so "requested" vs "actually ran" are both visible.
- **Value controllers respect scope**: controllers advance only on nodes inside the executed closure. Partial execution shuffles exactly the seeds it consumed and leaves the rest untouched - fixing the old frontend's bug where partial runs didn't advance seeds at all (and avoiding the opposite bug of shuffling seeds that never ran).
- **Extensible modes**: new modes are just new scope providers - queue-selected-outputs, queue-multiple-targets (server supports a list), and later "execute up to this non-output node" (requires injecting a sink/preview node into the compiled prompt or backend support - flagged as a backend collaboration item, since a synthetic node changes cache keys). The scope abstraction means a new mode is a command + a closure function, not new execution plumbing.

**Error reporting: one Diagnostic model, anchored to executions - not to the live graph.** The current frontend's error UX confuses because errors point at live-graph nodes that may have been edited, moved into subgraphs, or deleted since the run. Here every error is a `Diagnostic` with a severity, an **origin** (frontend compile, server validation reject, runtime `execution_error`), a full payload (exception type, message, complete traceback, inputs at time of error - the server already sends all of this; the old frontend just presents it poorly), and an **anchor**: document revision for compile/validation diagnostics, `prompt_id` + runtime node id resolved through provenance to a qualified occurrence for runtime errors. An optional `refs` list carries presentation-only graph/node/port/value identities: the stable raw message is never rewritten, while the app resolves current node titles, schema names, and port labels and keeps every raw id visible. Refs are ephemeral diagnostic data and are never serialized into workflow documents. Consequences that fall out:

- **Runtime errors live on the Execution object**, so the frozen view shows them permanently and exactly where they happened - the snapshot cannot drift out from under the error. On the live tab, error overlays follow the same rule as progress overlays (shown while lineage + semantic hash match; on divergence the frozen view remains the truthful record). Errors survive reload via `/history` status messages plus locally persisted snapshots.
- **One problems panel, all origins**: compile diagnostics ("muted node starves required input"), validation rejects (per-input `node_errors` details), and runtime failures appear together, grouped by their primary affected node using the same current title/schema-name resolution as each message. Node groups retain diagnostic first-appearance order, show their count and maximum severity, and are independently collapsible; unanchored entries collect in a final General group. Each anchored entry remains click-to-navigate - including through subgraph boundaries, since provenance yields the full occurrence path (navigate drills into the instance). Node badges mark erroring occurrences; collapsed subgraph instances aggregate (any-failed -> failed) with drill-in.
- **Details pane**: exception type + message up top, expandable full traceback, the node's input values at failure (already in the payload), and a one-click copyable report (node, pack, versions, traceback) - the thing users paste into GitHub issues today by screenshotting.
- **Nothing is dropped**: errors on runtime nodes with no display mapping (backend graph expansion) degrade to execution-level entries rather than vanishing, same policy as unknown-node progress events.

- Collapsed subgraph instances aggregate descendant states by explicit policy: any-running -> running, any-failed -> failed, cached only if all cached; progress indeterminate (no fake percentage averaging).
- Persistence: executions are recoverable best-effort from `/history` (prompt + embedded workflow); live progress timelines are session-only. Recent snapshots also persist locally (IndexedDB) so frozen views survive reload.
- **Reconnect + reconciliation (implemented)**: unexpected WS closes retry forever with exponential backoff (500ms doubling to an 8s cap - server restarts take a while); `disconnect()` is the only non-retrying close, and a stale socket's late close can never clobber a newer connection. Events missed during the gap are healed on every `connected` transition by `reconcileExecutions()`: the server's `/history` records each run's terminal WS envelopes verbatim (`status.messages`), so reconciliation **replays them through the same normalizer path live events take** - one event pipeline, no parallel recovery state machine, errors keep full tracebacks and provenance anchors. Non-terminal executions found in `/history` get their terminal transition + outputs; those still in `/queue` are left alone (the re-associated clientId resumes their events, and `progress_state` carrying the full per-node map heals the progress gap - the no-single-cursor contract paying off); those in neither are marked interrupted with an `execution.lost` diagnostic. Terminal races are safe by construction: only non-terminal runs reconcile and `markLost` never downgrades a terminal state. A failed reconcile lands in the problems panel, never a swallowed promise.
- Known protocol constraint (flagged, not solved here): the server sends execution events only to the submitting `client_id`. One app instance with many tabs shares one client_id, so tabs are fine. Separate browser windows won't see each other's live progress without polling `/history`/`/queue` or a shared-client scheme - acceptable v1 limitation.

**Concurrency: the model assumes parallel execution everywhere; nothing owns a "current" execution.**

- **Many executions in flight is the default case, not an edge case.** Because every event routes by `prompt_id` into its own Execution object, N concurrent prompts - same backend or different backends - each accumulate their own node states, previews, outputs, and errors with zero shared mutable state. Queueing the same workflow 5 times yields 5 independent Executions and 5 accurate frozen views.
- **Per-node state map, never a cursor.** An Execution's progress is `occurrence -> {state, progress, previews}` - there is no "the currently executing node" field anywhere in the model. The event normalization contract maps both the legacy one-node-at-a-time events and the newer `progress_state`-style multi-node payloads into this map. Consequence: when the backend gains branch-parallel execution (several nodes of one workflow running simultaneously), the frontend renders it correctly with no model change - multiple nodes simply show running states at once. This is a contract-level guard: no consumer (overlays, rails, aggregation) may assume at most one running node.
- **Overlay binding policy (implemented)** (the "which run does the live tab show?" question): a live tab binds to the **most recently submitted** Execution of its lineage by default ("follow latest"); semantic-hash divergence is surfaced on the sync chip (`in-sync`/`diverged`), never used to silently unbind. The executions rail carries a per-row **pin** control that binds the run's live tab (resolved by the run's lineage, never the active tab) to that exact run: new submissions do not steal a pinned overlay, and the chip gains a "Follow Latest" release action. One resolver - `executionForTab()` - feeds progress, node states, errors, previews, and the outputs panel, so a pin switches all of them atomically. Pins are per-tab VIEW state (`AppState.overlayPins`): never serialized, never a document command, dropped when the tab closes or its document is replaced, and validated so a pin can never cross lineages or attach to a frozen tab. In a future collaborative session this stays per-user presence state. Non-matching or unpinned executions still render fully in their own frozen views - the binding policy only decides the live tab's overlay, never where data goes.
- **BackendConnection is a first-class object (implemented).** The app holds a set of `Backend`s (`AppState.backends`; index 0 is the unremovable default), each owning: its own WS client + event stream, its own **schema registry** (backends can have different packs/versions installed - registries are never merged; frontend-only schemas layer over EVERY backend's registry), and its own scoped client (model lists differ per backend). Executions carry `(connectionId, prompt_id)` into the ONE shared ExecutionStore, so identical prompt ids on different servers never collide. A live tab has a **target backend** (`AppState.tabTargets` - per-tab VIEW state, never serialized; cleared when the tab closes or its document is replaced); compile records the target's identity and registry hash in the artifact, and submit/queue go through the tab's backend. Frozen tabs ignore targets entirely: they resolve their backend from `execution.connection`, and every runtime read - outputs, previews, `/view` URLs (`viewUrlForExecution`), history hydration - routes through the execution's OWN backend, never the active tab's. Queue depth is per connection (`queueRemaining` is a map), and reconnect reconciliation only inspects the reconnecting backend's executions - backend A coming back can never mark backend B's runs lost. Removing a backend keeps its historical executions AND their `/view` routing (a retired-backend map resolves URLs), retargets its tabs to the default, and deliberately never reconnects. The executions rail groups by backend only when more than one exists; single-backend users see none of this machinery - one implicit default connection.
- **Value controllers under parallelism**: controller advance happens at queue time and values are baked into the CompileArtifact, so parallel submissions can never race over seed state - each artifact records exactly what it ran with.

### 9. Previews as a built-in channel, not a hack

Custom packs like VideoHelperSuite have to fight the current frontend to show live/animated previews. Here, previews are a core concept wired into the execution model:

- Every node occurrence has a **preview channel**: a slot of derived state fed from three sources, all routed by `prompt_id` + provenance maps (so previews land on the right occurrence, in the right tab, and in frozen views):
  1. **Live sampling frames**: binary WS frames (types 1/4, with node metadata when the server supports it) - the in-progress latent preview stream.
  2. **Executed UI payloads**: the `executed` message's output (`images`, `animated`, `audio`, `text`, `result`/3D) and cached-UI replays, matching the V3 `ui.Preview*` wrappers.
  3. **Media resources**: files served via `/view`, streamed on demand (HTTP range requests for video/audio - real `<video>`/`<audio>` elements in the DOM overlay when playing, static poster frame drawn in-canvas otherwise).
- A **PreviewRenderer registry** (same extension pattern as WidgetKind) maps payload kinds to renderers. Core ships: image, animated sequence, video, audio, text, 3D (later). A custom pack that emits a novel payload kind ships a PreviewRenderer and gets rendering everywhere previews appear - node body, frozen views, queue rail thumbnails, later app mode - because all of those render the channel, not the node.
- Preview area is just a layout row in the node body (section 12), so it participates in sizing, collapsing, and culling like everything else.
- Budgets: latest-frame-only retention for live streams, capped animation buffers, offscreen channels drop to poster frames. Preview memory is a metered pool, not an accident.

**Input materialization ("peek") - assessed viable, exposure post-v1.** Rich-typed inputs (IMAGE first) can be widget-capable like any other port: an asset-reference WidgetKind (upload/pick/paste), value stored ID-keyed, compiled as a literal - no architectural change, just a registry entry. For *connected* inputs, an input's best available value can be resolved from prior executions without executing: hash the input's upstream cone (same memoized closure machinery as ExecutionScope) and compare against the same cone in each execution snapshot via provenance maps. Equal -> that run's output media is an **exact** materialization; unequal -> stale, shown dimmed with a provenance badge ("from run at T, upstream changed" - decided default; a settings toggle can suppress instead, and interactive approximation editors suppress stale inputs since editing against outdated pixels is the one costly case) - never silently wrong, which is what makes this safe where an "whatever image is lying around" heuristic would not be. "Materialize this input" is just partial execution targeting the feeding node. On top of peeked media, widgets/editors may declare an opt-in **interactive approximation** capability (e.g. crop-rectangle preview over the real upstream image, updating as values change client-side); approximations must be visually distinct from authoritative execution outputs at the design-language level. Known caveat: cone equality guarantees semantic identity, not bit-identity (GPU nondeterminism) - same caveat as the backend's own caching.

**Peek backend contracts (SHIPPED, Dinkster commit a58cdb6).** The frontend side of peek is pure document+snapshot computation; payload access rides two native-protocol capabilities: (1) `GET /api/values?clientId&jobId&nodeId&outputId` - runtime node ids verbatim (region paths included), optional `element=i,j` list descent, optional `rendition=<kind>`; JSON descriptor + declared rendition list without a rendition, raw bytes with one (`ETag "<fingerprint>/<kind>"`, immutable - cache client-side forever, conditional GET honored). Lookup identity is job/node/output - fingerprint is ONLY the cache-validation tag, never a fetch key. Refusals are structured and distinct (`unknown-*`, `not-retained`, `not-complete`, `evicted`, `no-rendition`) - an evicted value can never silently resolve to a newer one, which is the property peek's "never silently wrong" story rests on. Rendition kinds are registry-extensible per type (packs register through the same TypeRegistry door as atoms), so negotiation is generic over the declared list, never hardcoded to PNG. (2) **Inline small scalars**: completed-job descriptors AND `node_finished`/`node_cached` per-output summaries carry optional `value` for registry-approved JSON scalars (strings capped, lists never inline at top level, absence never inlines; omission means "not inline", never null) - int/string/bool peeks need zero round trips, including mid-run intermediates. Retention: bounded server job history + cache residency for intermediates; leaving history is a clean `unknown-job`. Which execution peek resolves against is the section-8 overlay binding (follow-latest or pinned) - no new selection machinery.

**Filesystem mounts backend contract (SHIPPED, Dinkster commit ddb4729).** The multi-directory replacement for ComfyUI's one-input/one-output-dir model; this is the surface a file-picker / mount-browser UX builds on. Read surface (always on when the backend serves with `--library-root`): `GET /api/mounts` -> `{"mounts": [{id, path, mode, source, state, entryCount?, error?}]}` with `state` pending|scanning|ready|failed, `mode` read|readwrite, `source` config|derived - real filesystem paths appear ONLY here (operator surface); documents never see them. `GET /api/mounts/{id}/list?path=<rel>` returns one level (`{"folders", "entries"}`) for folder navigation; `GET /api/mounts/{id}/entries?q=&cursor=&limit=` is the query-first cursor-paged catalog under the standing collection contract (cursor query-bound, 400 on mismatch, limit 1..500 default 100). Entry rows are EXACTLY the upload path's AssetRef fields plus `virtualPath` (`mounts/<id>/<relpath>`): `{virtualPath, name, digest, size, mediaType}` - so a browsed entry commits as a widget value through the existing ASSET path with zero decoder change. Previews: `GET /api/assets/{digest}` falls through from the upload vault to ready mounts (streamed, same ETag/immutable-cache contract) - no upload/copy needed. Mutation is policy-gated, not absent: `POST /api/mounts {id, path, mode?}` -> 201 descriptor, `DELETE /api/mounts/{id}`; without `--allow-mount-changes` both answer 403 `{"error": "mount-changes-disabled"}` (machine-readable, engine-not-ready mold - distinguish policy from missing endpoint and hide/disable the grant UI accordingly). Grants are durable immediately (mounts.toml), visible as a pending row at once, scanned in background; derived mounts (comfy-input read-only, comfy-output readwrite, auto-derived from `--comfy-root`) refuse runtime deletion with 409. Event: every mutation and finished scan publishes non-droppable `{"type": "mounts_changed"}` - a refetch ping for `GET /api/mounts`, never a diff (no epoch; the list is tiny). Workers resolve mounted digests live via an engine-republished snapshot file - no restart. Writes shipped separately as structured save targets (next paragraph).

**Structured save targets / schema wire v5 (SHIPPED, Dinkster commit 6b9d874).** Schema wire 5 is additive over v4: one new per-input widget descriptor `{"type": "SAVE_TARGET", "suffix": ".png"}` (`suffix` omitted when empty; our decoder normalizes it to `''` so consumers read one shape). The v4 ASSET descriptor is byte-for-byte unchanged, and widget metadata stays excluded from schema signatures (presentation, never identity). A save destination is structured DATA, never a raw host path: `{"mount": "<mount-id>", "prefix": "sub/dirs/stem"}` with strict grammar - mount id follows the backend mount/name grammar (lowercase `^[a-z][a-z0-9]*(?:[-_][a-z0-9]+)*$`), prefix is /-separated relative, the last segment is the filename STEM (the node owns the extension via the widget suffix); absolute paths, backslashes, empty segments, `.`, `..`, and raw strings all refuse loudly on both sides (frontend: `saveTargetIssues` in `@dinkster/widgets`, shared by the widget kind's validate() and the editor's commit gate). `dinkster.save_target` is an ordinary concrete socket atom: exact typed producer links render, connect, save/reopen, and compile without special frontend semantics. A connected SAVE_TARGET row is read-only and retains its dormant structured value underneath until disconnect; the ordinary companion source identifies the producer even when the backend has no inline structured summary to display. `core.string` is not compatible in either direction and the frontend never interprets one as a target, host path, or prefix. Link-drop therefore refuses direct string/save-target edges. The catalog inspected on 2026-08-06 advertises no string-to-save-target converter, so the frontend offers none; enabling conversion requires an ordinary backend-advertised node with a `core.string` prefix input, an authoritative mount choice/default, and a `dinkster.save_target` output. Picker eligibility: mount choices come from `GET /api/mounts` rows with `mode === "readwrite"` and `state === "ready"`, fetched fresh on every editor open because grants/revokes apply live (the very next save) with no restart. Native `dinkster.save_image` takes optional `target: dinkster.save_target` (default `{"mount":"comfy-output","prefix":"ComfyUI"}`, suffix `.png`), outputs `assets: list<dinkster.asset>` as the same AssetRef wire uploads use, and a saved output's digest resolves through `GET /api/assets/{digest}` the moment the job completes (writes sidecar - immediate readback, no rescan). V1 LiteGraph SaveImage import preserves its `filename_prefix` string value; compatibility conversion at the API-prompt boundary (including refused `%date%` substitution) does not create frontend type coercion. Frontend implementation: decoder in `dinkster-wire.ts` (accepts wire 3/4/5), `SAVE_TARGET` kind + `core.saveTarget` view in `@dinkster/widgets`, mount-picker editor in `CanvasHost` (null commit = unset optional target, schema default applies server-side; a stored mount currently not writable is offered as "(unavailable)" rather than hidden - the backend stays authoritative at execution), covered end to end by `e2e/save-target.spec.ts` over an intercepted `/api/mounts`.

**DynamicSlot native wire / schema wire v6 (SHIPPED, Dinkster commit c2ac572).** Schema wire 6 is additive over v5: one new interface role, `{"role": "dynamicSlot", "id", "required"?, "variants": [{"key", "type": <TypeExpr>, "inputs": [<input entries, same shape as role=input minus the role field>], "doc"?}], "doc"?}`. Variant keys use `[A-Za-z0-9_-]+` (NOT the lowercase name grammar - the backend reversed its earlier proposal); variant types are recursively concrete ("any of several" is spelled as several variants). Identity model, per the settled contract: stored DynamicCombo and DynamicSlot choices are DOCUMENT state, authoritative for the backend's elaborated interface, and travel ONCE per node on the graph wire as `"slotVariants": {"<materializedConstructPath>": "<key>"}` (sibling of `inputs`, omitted when empty) - never per-input. DynamicCombo retains its flat selector in the compatibility prompt, while native lowering removes that duplicate input after recording the choice. Fresh nodes persist their first DynamicCombo choice; compile refuses a missing stored choice instead of converting the UI's legacy first-option display fallback into schema/cache identity. Prompt ids are construct-local: the slot socket submits under the slot id (`source`), dependents as `<slotId>.<local>` (`source.prefix`) - the earlier variant-qualified `slot.<key>.x` proposal is superseded. Frontend document value keys keep the bracket branch syntax (`slot.[key].x`, like combo branches) so switching variants never reinterprets stored values; the wire name is compiler output, never identity. Two variants of one slot MAY reuse a dependent local (mutually exclusive by construction); a frontend-modeled shared dependent colliding with a variant local is diagnosed and the variant input skipped (native v6 has no slot-level shared dependents - always-revealed knobs are ordinary static inputs). Cache identity: the backend's elaborated schema carries `slotChoices` into its schema signature, so switching variants is a cache miss even between byte-identical interfaces - which is why the choice must travel whenever the slot participates in the prompt, including zero-dependent variants. A DISCONNECTED slot's stored choice stays inert (not emitted): the backend elaborates dependents from the choice, and submitting a choice whose dependents the prompt does not carry would bounce; a disconnected optional slot with no traveling choice contributes nothing, which is the contract's own story. Compile fails loudly (`compile.slot.missingVariant`) when a connected variant-bearing slot has no stored choice or stores an unknown key - both are deterministic elaboration-failed errors backend-side, surfaced early and anchored. Runtime type mismatch stays the ordinary advisory warning (the backend never re-dispatches variants). The old `compile.slot.variantUnsupported` v5 gate is retired. Frontend implementation: decoder in `dinkster-wire.ts` (accepts wire 3/4/5/6), elaboration emits construct-local api names, compile emits `slotVariants`, recipe identity includes stored choices, `dinkster-connection` follows only stored active branches while filtering native selectors and passes `slotVariants` through verbatim.

**DynamicSlot + MatchType binding / schema wire v32.** A required closed top-level DynamicSlot may carry `"typeTemplateId": "T"`. Its stored selected variant binds that node-level TypeExpr variable, and every active input/output occurrence of `T` resolves to the variant's recursively concrete type, including occurrences below list/asset constructors. One slot may bind a template id, at least one output or output-family must use it, and each output occurrence's allowlist must admit every variant. The slot choice already participates in computation identity; the binding adds no graph-derived identity or solver-to-elaboration feedback. Subgraph boundaries project the selected concrete type through exposed dependents and outputs; directly forwarding the specialized slot itself retains the existing `boundary.specializedSlotUnsupported` refusal because that would move occurrence-local choice onto the shared definition schema. Older schema wires reject the field instead of silently exposing an unresolved dependent output.

**Exact integer bounds / schema wire v33.** A NUMBER descriptor on `core.int` carries min, max, and step outside JavaScript's safe-integer range as canonical decimal strings; safe integers remain JSON numbers and `core.float` remains number-only. INT widget state likewise stores a safe number or an exact decimal string from signed 64-bit minimum through unsigned 64-bit maximum. Submission lowers an unsafe value to `{"$int":"..."}` only when the backend advertises `decimalInt` in `dinkster.graphFeatures`; otherwise compile refuses the input instead of rounding it. Steppers, after-generate controllers, app-view controls, validation, serialization, and reload all preserve the exact value. Older schema wires omit unsafe constraints, so old clients never receive an imprecise JSON number.

**Node discoverability terms / schema wire v8 (SHIPPED, Dinkster commit d36d2c9).** A node schema may carry `searchTerms: string[]`, omitted when empty; the decoder normalizes omission to an empty array. These terms are presentation-only vocabulary for node discovery, never node-resolution aliases, and may collide freely. They are excluded from backend schema signatures and all identity. The node palette gives them the same weight as type ids and ComfyUI search aliases, below display-name matches, while retaining the shared exact, prefix, word-prefix, substring, and typo tiers.

**Node palette discovery and link insertion (SHIPPED).** Input and output type controls are searchable multi-selects: selections are ORed within a direction and the active input/output groups are ANDed. A base atom discovers recursively wrapped `list<T>` and `asset<T>` ports without changing connection compatibility; explicitly structured tokens remain structure-exact. Slash-delimited schema categories render as a counted, collapsible folder tree and folder selection includes its descendants. Reroute is a synthetic utility entry and can terminate an empty-canvas noodle drop atomically. Double-clicking an ordinary noodle now offers either the former `reroute.insert` action or an `Insert node...` palette constrained in both directions; insertion disconnects the original noodle and reconnects both sides in one command batch. Link-drop creation requires a closed TypeExpr anchor, so an untyped dangling end, missing schema, or failed fresh elaboration never produces an accept-all palette or arbitrary auto-connect. Candidate matching uses the fresh elaborated surface rather than an Autogrow wrapper: concrete and constrained variables filter exactly, while intentionally wildcard or unconstrained generic ports remain valid deterministic fallbacks after compatible closed-domain ports. List/scalar cardinality remains exact. The fresh elaborated target, any required Autogrow materialization, and `link.connect` stay in the same node-add batch.

**COMBO widget descriptor / schema wire v14 (SHIPPED, Dinkster commit 0da7292; supersedes the v13 presentation-marker design).** The descriptor remains `{"type": "COMBO", "options"?: ["euler", ...], "remote"?: {"route": "/api/...", "refreshButton"?: true}}`, with the same static and remote validation and replacement semantics. Its socket is now the ordinary concrete atom `core.combo`, carrying a plain string payload. Direct core.string<->core.combo links are hard-invalid in both directions; the two converter nodes are the only bridge. Combo-to-combo is always legal regardless of option lists, and membership remains execution-time validation. The retired comboSource marker and its provenance walk no longer exist. Pins, widget taps, noodles, reroutes, lenses, palette previews, and tooltips all derive COMBO presentation directly from canonical core.combo. No migration machinery is provided.

**Labeled booleans / schema wire v10 descriptor (SHIPPED, Dinkster commit 1007114; current schema wire v14).** Stale v7-v9 payloads refuse loudly - one current version at a time, flipped in a single coordinated restart with the backend (legacy additive v3-v6 fixtures still decode). A fourth widget kind, only ever on `core.boolean` inputs: `{"type": "BOOLEAN", "labelOn"?: "enable", "labelOff"?: "disable"}` - optional strings omitted when empty, never both absent (a label-less boolean carries no widget; the type alone means "render a toggle"). Presentation only, never identity. The compact toggle renders the custom label for the current side, falling back to true/false per side when a label is missing. Backend translation (shipped alongside): boolean-like two-option v1 combos - enable/disable, on/off, true/false, yes/no, either order, case-insensitive - become real `core.boolean` inputs wearing the original strings as labels, with `execute()` mapping the boolean back to the legacy vocabulary; raw legacy strings still submit unchanged. The frontend's half of that story is a document migration (`normalizeLegacyBooleans` in `app-state.ts`): stored STRING values on BOOLEAN-widget inputs matching exactly the eight recognized tokens are rewritten to real booleans in one undoable batch (surfaced as `upgrade.legacyBoolean` in Problems); anything else is left alone for the `widget.BOOLEAN.badValue` advisory. Unlike replacement upgrades (strictly once per tab), this pass RE-ARMS on explicit backend retarget: which schemas interpret a document is the tab's target backend, and a document opened while targeting a backend where its types don't resolve can later be pointed at the backend its strings were written for. The pass is idempotent and only rewrites the exact tokens, so retarget re-runs are safe; a mere schema refresh never re-arms it, so an undone migration stays undone within a session.

**Portable preview kernels ("mirror" tier) - future direction, hook designed now.** Precedent: core's GLSLShader node authors in GLSL ES 3.00 *because* the same source runs in the browser (WebGL2) for live preview and on the backend (desktop GL/ANGLE) at execution - one implementation, two executors. Generalized: a node schema may declare a **portable kernel** (GLSL ES 3.00 now; WGSL/WebGPU via `wgpu-py` and WASM for non-GPU ops later) that IS its backend implementation; the frontend executes the same source over peeked/materialized inputs for live feedback. This defines a preview-fidelity ladder: *approximation* (client-only reimplementation, opt-in, visibly approximate) < **mirror** (same kernel both sides - semantically exact by construction; WASM can be bit-exact) < *authoritative* (execution output). Kernels compose: a chain of kernel-bearing nodes (crop -> color -> LUT) live-previews end-to-end from one materialized input without queueing. Constraints: kernels are declared schema data executed in sandboxed substrates (shader/WASM - no arbitrary JS on the backend, which would add a runtime + sandboxing problem while still not matching torch semantics); frontend execution runs in workers/GPU under the preview memory/compute budgets; graceful fallback to approximation/authoritative tiers when WebGPU is absent. v1 ships the *hook* (schema field + fidelity-tier semantics in the design language); kernel execution is post-v1. **Kernels are pack-extensible from the moment they ship (decided)**: any node pack may declare kernels through the same schema field core uses - a core-only capability would just push packs back into hand-rolled canvas/DOM preview hacks, recreating the old ecosystem's failure mode. The safety boundary is the substrate (sandboxed shader/WASM execution, budget-metered), not the author. What protects evolvability instead: the kernel declaration is **versioned** (`kernelVersion` + substrate id), unknown substrates/versions degrade gracefully to the approximation/authoritative tiers, and the declaration schema follows the format's additive-first evolution policy.

### 10. Widget system: pluggable by contract

Widgets are the main extension surface, so they get a real interface instead of being core-owned special cases. The contract is split in two, because the old frontend's mistake was fusing them: **what a value is** (semantic) and **how it is presented** (view) are separate registrations:

```ts
interface WidgetKind<V> {                // semantic: one per widget_type
  type: string                          // matches widget_type from the node schema
  valueSchema: ValueSchema<V>           // JSON-serializable, versioned, migratable
  defaultValue(spec: WidgetSpec): V
  validate(value: V, spec: WidgetSpec): Diagnostic[]
  defaultView(spec: WidgetSpec): ViewId // chosen from schema hints (multiline, display: slider...)
}

interface WidgetView<V> {                // presentation: one or MANY per kind
  id: ViewId
  kind: string                          // which WidgetKind this view presents
  isCompatible(spec: WidgetSpec): boolean   // e.g. slider view requires min/max
  measure(spec: WidgetSpec, env: TextMetrics): Size
  drawCompact(ctx: SceneBuilder, value: V, spec, state): void   // in-canvas rendering
  hitRegions?(...): HitRegion[]                                 // inline interactions (drag a slider, toggle)
  editorUi?: HostUiProviderV1            // focused/expanded declarative UI
}
```

`HostUiProviderV1` also accepts one root-only Asset Editor presentation node.
It carries bounded display fields, authored origin labels, supplied capability,
notice, fact, tool, and generic command state. The host owns the responsive
viewport, Inspector/Editor regions, focus, ARIA, styling, and no-payload command
lookup. It fails closed for unknown field and capability kinds. Transform,
media-operation, progress, output-fact, provenance, draft, gesture, payload,
and route semantics remain outside the frontend contract.

**Click-to-expand: node size is never a readability requirement.** A design smell the current frontend normalizes: content (long prompts, file paths, combo labels, previews) gets clipped by the node's box, and the user's only recourse is manually resizing the node. Here the compact and expanded representations are decoupled by contract:

- `drawCompact` renders within the widget's row and truncates *honestly* (ellipsis/fade affordance signals hidden content) - it never dictates how much content the user can see.
- Activating a widget (click/Enter) opens its `editorUi` tree in a **core-owned overlay anchored to the widget but sized independently of the node**. The view declares sizing preferences; core owns placement, focus, dismissal, rendering, and command invocation.
- The same path works **read-only**: on frozen views and locked documents, activation opens the editor in inspect mode (select/copy enabled, commit disabled). Reading a long prompt on a frozen snapshot requires zero layout changes.
- Expansion is transient UI state - not view state, not semantic state. Nothing serializes; the node's layout is untouched. Manual node resizing remains available as a *layout* preference (how much space you want a node to occupy in the composition), but is never the price of legibility.

**Views are user-switchable.** The STRING single-line/multiline split is the canonical case: it is one value kind with two views, not two widget types. The node author's `multiline`/`display` hints select the *default* view; any widget with more than one compatible view gets a "change view" affordance, and the user's choice is stored per widget instance in **view state** (not semantic state - it never touches the semantic hash, compilation, or the value itself, and switching views is always lossless). Same mechanism covers INT/FLOAT as field vs. slider vs. stepper, COMBO as dropdown vs. radio row, color as swatch vs. hex field - and later, app-mode bindings picking a different view of the same widget than the graph shows. Extensions can register additional views for existing kinds (a fancy prompt editor for STRING) without touching the kind or the nodes that use it - the view registry is open in both directions: new views for existing kinds, and new kinds with their own views. If the schema ever needs to *restrict* which views a widget allows, that is one additive optional field (`allowedViews`) checked alongside `isCompatible` - designed for, deferred until needed.

**Value controllers (control_after_generate, done right).** The seed-randomization feature is the canonical example of state that the old format mangles: it is a phantom second widget occupying a positional `widgets_values` slot, mutated as a hidden side effect of queueing. Here it is a first-class concept:

- A schema flag (`control_after_generate` on INT, `control_after_refresh` on COMBO, open to other kinds) gives the widget spec a **controller slot**. Controller state (`fixed | increment | decrement | randomize`) is stored as ID-keyed structured state alongside the value - never a second widget, never positional.
- The mutation is a **document command emitted by the queue flow**: compile + snapshot first (the executed value is captured), then apply the controller's mutation through the normal command layer. It is undoable, visible in history, and cannot desync anything because it is not a side channel. Controllers advance **only within the queued ExecutionScope** (section 8) - partial execution advances exactly the seeds it used.
- Presentation is the view's choice: the default INT-with-controller view renders one combined row (value + compact mode adornment, the Nodes 2.0 look); a two-row view or a bare view (controller hidden, e.g. in app mode) are just other views of the same state.
- Interaction with frozen views, resolved rather than accidental: a randomize controller means the document diverges from the execution *immediately* after queueing - which is exactly when the frozen snapshot (holding the executed seed) matters. The divergence badge distinguishes "advanced only by controllers" (soft state, expected) from real user edits, by checking whether the semantic diff touches anything beyond controlled widget values.

**Remote-valued widgets (remote combos and kin) - a first-class contract, because they break purity if handled ad hoc.** The pipeline claims elaboration/validation are pure functions; remote options are IO. The resolution is to make the remote data an explicit *input* to the pipeline instead of letting widgets fetch:

- Schema declares a **RemoteSource**: route, params (which may reference *other widget values by ID* - dependent combos like "files in the folder chosen above" - declared as dependencies, so refetch is reactive, never polled), TTL, refresh triggers (on editor open, on execution completed, manual), and pagination/search hints.
- A single **RemoteSourceService** owns all fetching: deduplicates identical route+params across nodes, caches with TTL, exposes each source as explicit state - `loading | ready(options, fetchedAt) | stale(options, error) | unavailable(error)`. No widget ever fetches directly; effects live in one place.
- Derived state consumes the cache as a third input: elaboration/validation are pure over `(document, schemaRegistry, remoteCache)`. A cache update is just a new input revision flowing through the same signal graph.
- **Values are never hostage to option lists.** The stored value is authoritative; an absent/loading/changed option list yields a diagnostic ("value not in current options" / "options unavailable"), never a value reset or block. Raw-value editing is the fallback view when a source is unavailable. This kills the classic failure mode of combos self-clearing because a list loaded late.
- Compile does not require sources to be loaded: values serialize as literals regardless; unverifiable membership is a warning-level diagnostic, and the server remains the final validator (it already is).
- Snapshots/frozen views store only the chosen value, never fetched lists; frozen views render values as-is with zero fetching. Multi-window: the cache lives with the authoritative store in the shared process.
- Security (hardens risk item 5): same-origin routes only, TTL respected, no auto-fetch on schema load - fetch on first editor open or explicit refresh.
- `control_after_refresh` composes: it is a controller on the widget whose trigger is the source transitioning to fresh `ready`, going through the normal command layer like `control_after_generate`.
- **RemoteSource generalizes to pack services.** Node packs register backend routes today (VHS: `/vhs/queryvideo` metadata, `/vhs/viewvideo`//`vhs/viewaudio` path-streaming with transform params, `/vhs/getpath` autocomplete) and the frontend hits them ad hoc. Here a pack declares typed **services**: *queries* (JSON request/response, e.g. media metadata) and *media resources* (streamable route templates consumed by PreviewRenderers/widget views). All go through the same single IO service - same-origin, cached, deduped, explicit states - and are the ONLY network access WidgetKind/PreviewRenderer code gets (the contract passes a scoped client, not `fetch`). `getpath`-style autocomplete is just a RemoteSource with dependent params.

Rules that make widgets "just work" everywhere:

- **The document stores only the value** (per `valueSchema`), never widget objects. Serialization, undo, copy/paste, semantic hashing, promotion into subgraph boundaries, named-net compatibility, and future app-mode bindings all operate on the value + schema - they never call widget code. A widget therefore works in every context automatically, because no context depends on it.
- **Value writes go through registered commands**; declarative actions carry only a command id and JSON payload. A widget cannot mutate the document, other nodes, or graph topology.
- **Rendering is two-tier**: `drawCompact` paints the cullable in-canvas representation; `editorUi` supplies a strictly decoded declarative tree that the host renders only while focused. One live editor at a time.
- **Core widgets eat the same dogfood**: INT/FLOAT/STRING/COMBO/color/curve/bbox etc. are implemented as WidgetKinds through the public registry with zero private APIs. If core needs a hook a custom widget can't have, that is a contract bug to fix, not a shortcut to take. This is the single best forcing function against the old frontend's "core cheats, extensions hack" dynamic.
- **Unknown widget types degrade gracefully**: value preserved and round-tripped, rendered as a read-only JSON/generic editor, diagnostic shown.
- Backend nodes select widgets by `widget_type` string, so a custom node pack can ship a backend node + a WidgetKind and have it work in graph view, subgraphs, and later app mode with no further integration.

### 11. Extension architecture: capabilities, not access

The old frontend's extension model failed because extensions and core share one mutable object graph. Here, extensibility is **typed registration points + the command API**, and nothing else:

- Registries: `WidgetKind`, node badges/overlays (execution decorations, price badges), declarative host UI providers, commands + keybindings + menu contributions, and importers/exporters.

**Menus, surfaces, and interactions are contribution points - the anti-hack contract in detail.** The current frontend's #1 monkey-patch magnet is menu code (every pack wraps `getNodeMenuOptions`), because there is no declared way in. Here every user-facing surface is a declarative **contribution point**, VS Code-style:

- **Menus**: every context menu (node, port, widget, link, named net, group, control surface, selection, canvas, tab, executions rail, subgraph breadcrumb) and every menubar/toolbar is an anchor accepting contributions: `{command, group, order, when}`. The `when` clause is a declarative context expression over read-only selectors ("selection contains subgraph instance", "port type is IMAGE", "execution running") - evaluated by core, so a contribution cannot run code just to decide visibility. Groups + ordering are specified, so packs cannot fight over placement; core's own menu items are contributions to the same anchors (dogfood rule again - if core can special-case its items, the contract is broken).
- **Surfaces**: sidebar panels, bottom panels, dialogs, settings pages, status-bar items, and empty-state actions use registered declarative providers. Providers receive frozen data and return typed content and commands; the host owns elements, styles, placement, focus, and lifecycle.
- **Interactions**: keybindings bind to commands through the same keymap (user-remappable, conflict-surfaced, never `addEventListener` on the canvas). Canvas gestures are NOT freely interceptable - that is the hack vector that makes packs break each other. Instead: drag-and-drop accepts declared payload handlers (drop a file/asset/library entry -> command), and custom canvas *tools* (marquee-like modes) are a registered capability with enter/exit lifecycle, one active at a time, arbitrated by core.
- **The escape-hatch rule**: there is deliberately no "give me the DOM/canvas and I'll wire it myself" API. When a pack cannot express something, that is a feature request against a contribution point - the same pressure-on-the-contract policy as the rest of the API. Hacks are prevented by module boundaries (core does not export internals), and kept unnecessary by making the declared path genuinely cover the use cases packs have today (audited against rgthree/KJNodes/VHS/pysssss menu and panel usage before freezing API v1 in extension API implementation). That audit is done: see `node-pack-extension-audit.md` for the usage-weighted coverage matrix, the confirmed gaps (widget interaction envelope, result channel, link/widget-row menu anchors, backend route/event contract, annotations), and the recorded refusals with their declared alternatives.
- Extensions read state through the same read-only selectors the UI uses, and write exclusively by dispatching commands (which enforce invariants and produce undo patches). There is no path to core internals - the core package simply does not export them. "No dirty hacks" is enforced by module boundaries, not review policy.
- The API surface is versioned and small (deep module: small interface, big implementation). Anything not expressible via the API is a feature request against the API, which keeps pressure on the contract instead of on workarounds.

**Per-contribution gating (decided): pack frontend features are individually toggleable.** The old ecosystem's features are side effects of executing pack JS, so the only off switch is not loading the pack - which is why cloud hosts drop whole packs (rgthree) over frontend behavior they cannot isolate. Here the registration model makes gating structural:

- **Manifest-first**: a pack enumerates every contribution (widget kinds/views, menus, panels, commands, keybindings, badges, tools, importers, services) in a manifest with stable namespaced ids (`rgthree.panel.groupMuter`) - the host enumerates contributions BEFORE activating pack code; nothing is contributed implicitly.
- **Enable state at three granularities**: whole pack frontend, contribution category ("all panels from this pack"), individual contribution. User settings locally; a **deployment policy** (allowlist/denylist over ids and categories) for embedding hosts. Registries support dynamic add/remove (the multi-window story already requires it), so disabling unregisters cleanly. Because there is no raw DOM/canvas escape hatch, a disabled contribution has no path back in - enforcement is module boundaries, not trust.
- **Nodes and frontend features are independent axes.** Disabling a pack's panels/menus/widgets never blocks its NODES: unknown widget kinds already degrade gracefully (value preserved, generic editor, diagnostic), surfaces just vanish. A host can run a pack's backend nodes with zero of its frontend riding along - exactly the case cloud could not express.

**Cross-pack widget and type reuse (decided): namespaces + declared dependencies.** Widget selection is by `widget_type` string through the open registry, so reuse across packs is inherent; the value contract (versioned, migratable valueSchema) - not rendering code - is the reusable unit, which is what makes reuse survive serialization, undo, promotion, and app mode. The rules that keep it from re-deadlocking:

- **Namespacing by construction**: widget kind ids and type atoms are namespaced by pack id (`kj.curve`, never bare `CURVE`); core owns the un-namespaced set; duplicate registration is rejected with a diagnostic. Collisions become impossible rather than reviewed away.
- **Declared dependencies, not bundling**: a pack manifest declares `uses: ['kj.curve']`. An absent or disabled provider triggers the standard graceful degradation, with the diagnostic naming the missing provider. A "widgets pack" is therefore not a special concept - just a pack whose manifest ships only WidgetKinds/views/PreviewRenderers and no nodes; that is the encouraged shape for shared ecosystems.
- **Extension without patching**: tweaking another pack's widget is either registering a new VIEW for the existing kind (open in both directions already) or forking the kind under your own namespace. Patching someone else's registration does not exist as an operation.

Out of scope for now: hard sandboxing/isolation of third-party JS (same-process trusted extensions first, like today's ecosystem). The contract is compatible with iframe/worker hosting later because pack code never holds core objects - values in, commands out - so hosts needing hard isolation can add it without an API break.

### 12. Node presentation: schema-driven layout with a real design language

The representation of a node is a **pure layout function**: `(elaborated interface, schema presentation constructs, view state) -> row stack`. No layout state is stored on nodes beyond position/size and per-view flags (collapsed sections, pinned previews). Because it is a function of the elaborated interface, dynamic inputs/outputs, conditional groups, and collapsible sections compose for free - a section containing a variadic family just yields more rows when the family grows.

The node body is a vertical stack of typed rows:

```diagram
+---------------------------------+
| * Title                  badges |  header (type color, deprecated/
|                                 |  experimental badges)
| o model                LATENT o |  paired row (input + output, the
| o positive              MASK  o |  classic default)
| o negative                      |  input-only row
| > advanced  [section v]         |  section header (collapsible)
|   o image_1                     |    member of variadic family
|   o image_2                     |    member of variadic family
| steps        [    20        ]   |  widget row (full width, never
| sampler      [ euler      v ]   |  shared with an output pin)
| +-----------------------------+ |
| |        preview area         | |  preview row (channel-fed)
| +-----------------------------+ |
+---------------------------------+
```

Resolving the same-line dilemma:

- **Input/output pairing on one line is the default** - it is familiar and conserves vertical space, and most nodes are fine with it. The classic two-column look is preserved.
- **Widgets always own the full row width.** This is the invariant that kills the old ugliness: an output is never placed beside a widget row.
- Those two rules compose in the layout function: outputs fill slots opposite connection-input rows top-down; only **overflow outputs** (more outputs than pairable rows, i.e. the ones that would have collided with widgets) get their own dedicated rows (decided default - a compact pin stack was judged potentially confusing and is deprioritized to an initial implementation curiosity prototype at most). The common node never changes; the problem case resolves itself.
- **Deviating is the explicit part**: schema hints can opt a node out of pairing (e.g. outputs-in-header compact template, or a specific output pinned to a specific row) where that reads better. Default stays classic; alternatives are opt-in.
- To be validated with visual prototypes in initial implementation/editing implementation against real workflows; the row model itself is the commitment, the default template is tunable.
- **Rows never grow to fit content; depth lives in the expanded editor.** Rows have fixed, type-appropriate heights (a multiline string gets a few preview lines, not its full text); anything deeper is one click away via the widget's expanded overlay editor (section 10). Node resizing is a composition preference, never the price of reading a value - the current frontend's "resize the node to read your own prompt" pattern is explicitly designed out.
- **Auto-size by default, manual resize as an explicit override.** A node's natural size is a pure function of its row stack (schema + active views + design tokens) - new nodes always spawn correctly sized, nothing ever spawns clipped, and interface changes (variadic growth, section collapse, view switch) re-derive the size automatically. Manual resize stores an override in layout state (width freely, within a minimum that never clips pins/rows; extra height renders as padding); an overridden node keeps its size across interface changes, and "reset to auto size" (context menu / command) clears the override. Since size is derived-unless-overridden, most documents never serialize sizes at all.

**Badges are interactive, by contract.** A badge registration is not just a glyph: it declares optional **popover content** (info rendered on click/tap - same row/section machinery) and **actions** (commands, shown as popover buttons). One contract covers all of them uniformly: the subgraph instance badge ("1 of N") opens instance count + jump-to-other-instances + **detach**; the error badge opens that occurrence's diagnostics with jump-to-problems-panel; the divergence badge summarizes what changed vs. the execution (controller-only vs real edits) with open-frozen-view; the deprecation badge shows the successor + apply-replacement; a stale-peek badge shows run provenance + materialize. Because badge actions are ordinary commands, they are undoable, keyboard-accessible via the command palette, and extensions registering badges get interactivity through the same declaration - no custom canvas hit-testing.

**Modified-from-default indicators + reset, derived not stored.** Anything that hides widgets (collapsed sections today; other folding surfaces later) must not hide the fact that hidden values were tuned - a loaded workflow's collapsed "advanced" section may hold exactly the values that matter. The rules:

- **"Modified" is a pure derivation, never serialized**: a widget is modified when its stored value differs (canonical JSON equality) from the *live* schema default. A missing values key means "at the default" (compile fills defaults for absent keys), so it is not modified. No dirty flags in the document, so no migration and no format change - and the semantics stay correct across schema versions: loading never mutates values, stored values always win, and a value equal to an OLD default but different from the CURRENT one honestly reads as modified, because it does differ from what a freshly added node gets today.
- **Exclusions that keep the signal honest**: widgets with no schema default (nothing to compare or reset to); controller-slotted widgets (control_after_generate/_refresh - their values advance by design every queue, so default-comparison is permanent noise; a future schema flag can opt one in); DynamicCombo selector rows (their value is dynamic state, not node.values); ghost/unmaterialized dynamic members (nothing persisted yet). Connectivity is ignored: a connected widget's dormant value still serializes and returns on disconnect, so it counts.
- **Collapsed sections render a subtle indicator** (small dot on the header strip) when they hide one or more modified widgets - only while collapsed; an expanded section shows the widgets themselves. The count rides the layout row (`hiddenModified`), so any renderer or test can read it without re-deriving.
- **Reset writes the current default EXPLICITLY - never deletes the key.** A deleted key would silently track future schema defaults and break exact reproduction, the workflow format's first duty. Reset means "make this widget equal to a freshly added node today"; restoring version-X semantics after a default change is the deprecation/replacement system's job, not reset's. Undo restores the pre-reset value.
- **Reset ships at three scopes through the menu registry** (widget / section / node targets), not hardcoded app chrome. The items are schema-aware, so they are a contribution FACTORY over a schema resolver closure - MenuContext itself stays plain data. Multi-widget resets dispatch ONE schema-blind `node.setValues` command (atomic, one undo step, skips already-equal writes so a fully-matching dispatch is a no-op with no undo entry); only modified widgets are written, so a section reset never pins explicit defaults onto untouched neighbors. Items hide when the target has no resettable widgets and disable when none are modified.
- Future: a clickable indicator popover (changed widgets, current vs default, per-item reset) rides the interactive-badge/popover contract above when that lands - it is NOT a one-off interaction.

**Resolved-value display (companion values) - decided, lands with peek/tap exposure.** A link-driven input's widget renders the value it *would* execute with, inline, in a visually distinct "propagated" style (read-only - the stored dormant value stays untouched underneath, per the disconnect-returns-your-value rule). Two derivation sources, one display contract: (1) **document-static chains** (value source / widget tap / alias chains ending in a literal) resolve at document time and are always exact - this is a pure compile-machinery query, no execution involved; (2) **runtime producers** resolve via peek (section 9) against the tab's bound execution, styled with the same exact/stale provenance distinction - a stale companion value shows dimmed with the run-provenance badge (interactive per the badge contract: shows source run, offers "materialize" = partial execution of the feeding node). Companion values are derived state, never serialized, and excluded from the modified-from-default signal (they describe the wire, not the stored value). Media-typed inputs render their companion as the peeked thumbnail through the ordinary PreviewRenderer registry - same pipeline, so pack-defined payload kinds get companion display for free.

Design language: a token system (spacing, typography, type-color palette, pin shapes, state styles) shared by canvas rendering and DOM widgets, so in-canvas and DOM presentation match. Standard row/section components mean "make these inputs a collapsable section" is one schema flag, not custom node code. Not everything needs to be semantically dynamic: purely visual simplifications (sections, separators, advanced-input folding, alternate compact templates) are schema-dictated presentation over the same document state.

### 13. Rendering: retained scene, canvas-first

- A retained scene graph derived from document + elaborated interfaces + solved types + layout; renderer-neutral primitives (shapes, text runs, hit regions) so the backend can be swapped.
- Canvas2D first with: viewport culling via a spatial index (also used for picking), budgeted LRU offscreen caching of expensive static node layers (scale-bucketed, not unconditional per-node surfaces), batched link drawing, text metric caching. WebGL is a possible later swap behind the same scene contract - not promised for v1.
- Widgets render in-canvas via `drawCompact` (crisp, cheap, cullable); the DOM overlay renders only the active view's host-owned declarative tree.
- No per-node framework components, no reactive mirrors, no layout CRDT. The shell owns everything around the canvas: tabs, sidebars, node library, queue rail, dialogs, settings.
- Performance budget from day one: benchmark workflows (1k+ nodes, heavy noodles) in CI with frame-time and memory budgets, starting at initial implementation.
- Accessibility decided now, not retrofitted: keyboard navigation model for canvas (focus follows selection, arrow/tab traversal), screen-reader exposure via an offscreen semantic list of nodes, standard DOM for all shell UI.

### 14. Shell framework: chosen on merit, and deliberately low-stakes

Two design moves make the framework choice small before making it:

- The core (document, derived state, executions) exposes its own **signal-based reactive store** in plain TS - not Pinia, not framework refs. The graph canvas subscribes to it directly with no framework in the hot path; high-frequency execution/progress updates never touch the DOM framework at all.
- Widget editors and extension UI return framework-neutral declarative trees, so third parties are not coupled to our shell choice.

What remains for the framework is genuinely shell work: tabs, sidebars, node library, queue rail, dialogs, settings, and eventually app-mode views. Evaluation on merit:

- **SolidJS**: fine-grained signal reactivity that maps 1:1 onto the core's signal store (external signals are first-class), no VDOM diffing tax, small runtime, TS-first. Weakest ecosystem of the candidates, but the shell's component needs (lists, overlays, forms) are modest.
- **Svelte 5 (runes)**: compiled fine-grained reactivity, excellent performance and DX, larger ecosystem than Solid; interop with an external signal store is fine but one step less direct.
- **Vue 3**: mature, signals-based under the hood (ref/computed), huge component ecosystem. More framework machinery than the shell strictly needs.
- **React**: largest ecosystem, but the coarse re-render model is the worst fit for a signal-driven core and would reintroduce the adapter/memoization discipline we are designing away.

**Decision: SolidJS first**, with Svelte 5 as the fallback. The initial implementation spike (tab bar + queue rail against the real signal store) becomes a validation gate for Solid rather than a two-way bake-off; Svelte 5 is tried only if the spike surfaces real friction. Because the core, canvas, and widget contracts are framework-free, a wrong call here is a contained rewrite of shell chrome, not of the product.

### 15. Views / app-mode readiness

Not built now, but the document is shaped for it:

- Every referenceable element (node occurrence, widget, output) has a stable qualified identity: occurrence path + semantic port/widget ID.
- A future `View` is a projection: an ordered set of bindings to those identities plus layout. The graph editor is itself "just a view" in architecture terms, though implemented natively.
- Output bindings will need an execution-selection policy (latest matching semantic hash / pinned execution / currently selected) - recorded as a design constraint so nothing in the execution model precludes it.
- Views must surface unresolved bindings (element deleted, dynamic port gone) rather than silently retargeting.

### 16. One workflow format (not two)

The old split - a litegraph-shaped "workflow format" with positional `widgets_values` arrays, plus a separate ID-keyed "API format" - is eliminated. The document format IS the workflow format, and there is exactly one:

- **Every value is keyed by stable semantic ID** (widget/port ID from the schema, member UUID for variadic ports). Positional arrays do not exist anywhere in the format. A node schema adding, removing, or reordering widgets cannot scramble values - unknown keys are preserved (with a diagnostic), missing keys get schema defaults, and schema-declared renames/aliases migrate old keys explicitly.
- **The API prompt is not a format; it is compiler output.** The flat `{id: {class_type, inputs}}` shape the server requires is produced by the compiler as a wire artifact (part of the CompileArtifact), deterministic and disposable - never authored, never stored as a source of truth. PNG metadata and `/history` embed the unified format. This is the honest limit of unification today: the server's wire contract stays as-is, but users and tools only ever touch one format. Long-term opportunity (backend work, out of scope here): teach the server to accept the unified format directly and the lowering disappears entirely.
- **Semantic/view split within the one format**: view state (positions, collapsed sections, named-net visibility, colors) lives in a distinct subtree from semantic state (nodes, values, links, definitions), so the execution-semantic hash is computed over a clean subset and "API-like" tooling can strip view data trivially.

**Translation, not dual support.** Old formats are import-only:

- litegraph 0.4/1.0 workflows (including `definitions.subgraphs`, reroutes-in-`extra`, floating links): translated on open. Positional `widgets_values` are mapped to IDs using the node schema's declared widget order - the same fragile mapping the old frontend does implicitly on every load, performed here exactly once, with diagnostics when the current schema's widget count/order disagrees. Native schema aliases still canonicalize immediately. Maintained `comfy_alias:<pack>/<class>` records instead decode against import-only compatibility-schema snapshots and then enter the ordinary replacement planner. Their snapshots never become executable or palette schemas. Clean alias replacements auto-apply as one atomic cohort; one unsafe alias holds the entire cohort for review. Top-level wire-15 Autogrow families preserve authored suffixes, order, values, controllers, links, and net sinks through family-aware rules. Unknown or ambiguous classes stay raw and diagnosed. See `docs/comfyui-workflow-translation.md`.
- API-format JSON: also importable - it already has IDs; layout is synthesized by auto-layout.
- KJNodes Set/Get pairs pattern-matched into named nets during import (best-effort).
- Legacy frontend PrimitiveNode -> value source (section 5b): value + controller state carried over as declared state, fan-out links as ordinary topology. Never-connected primitives with no adopted widget drop with a warning diagnostic. (Backend PrimitiveInt/Float/... nodes import as the ordinary compute nodes they are.)

**Upgradeability is designed in, since we WILL add things:**

- Explicit `formatVersion` with an ordered, tested migration pipeline (every released version N has an N -> N+1 migration; old files replay the chain). Golden corpus of real workflows runs through migrations in CI.
- Pre-release version policy: v1 is unstable until the first public release and breaking shape changes revise it in place (fixtures/tests updated) - we do not mint version numbers that only ever existed inside this repo. Upgradability stays actively validated by synthetic-step tests that exercise the full load path (detect -> migrate -> stamp -> validate -> invariants); the real migration chain starts at the first released version.
- Additive-first evolution policy: new capabilities (e.g. variadic output members, new presentation constructs) are new optional fields, not reinterpretations of existing ones. Breaking changes require a version bump + migration, never in-place meaning changes.
- Per-value versioning delegated to WidgetKind `valueSchema` migrations, so a widget can evolve its value shape without a format-wide bump.
- Namespaced extension data (`ext.<extensionId>` subtrees on nodes/graphs/document) preserved byte-for-byte through load/save even when the extension is absent - third parties get persistence without forking the format.
- The format is a published spec with a JSON Schema; the validator is part of the public core package so external tools can verify files.

### 17. Directed partial-execution scopes

Partial execution is derived from authored graph connectivity, never canvas
position. Reroutes are structural junctions rather than executable nodes, so
connectivity walks through them and returns real nodes only. Named nets count
as directed edges and every defined selector candidate counts during the
policy-independent selection analysis.

For a selected real-node set `S`, reachability is transitive over that
collapsed directed graph:

- **first / minima** are selected nodes with no distinct selected ancestor;
- **last / maxima** are selected nodes with no distinct selected descendant;
- **in-selection sinks** are selected nodes with no DIRECT collapsed edge to
  another selected node. This differs deliberately from maxima: a selected
  node connected to another selected node only through an unselected node is
  still a sink;
- **Execute up to** targets every minimum, producing the union of their
  upstream closures. Single-node behavior is unchanged; multi-selection now
  follows the explicitly defined minima rather than targeting every selected
  node;
- **Execute from onwards** finds the union of downstream closures of every
  maximum and targets every executable backend-declared output in that union.
  The backend still plans each target's complete dependency graph. Cache hits
  suppress unchanged dependencies; any dependency, including an ancestor or
  side input outside the downstream closure, may execute on a cache miss;
- **Execute between** is meaningful only when `S` has more than one node. Let
  `P = descendants(minima) intersect ancestors(maxima)`, endpoints included.
  The selection is contiguous exactly when `P == S` and the subgraph induced
  by `P` is one weakly connected component. This directed-convexity rule
  includes every branch of a diamond and rejects holes, disconnected chains,
  and singleton selections. Execute between submits the in-selection sinks as
  ordinary partial targets. The scope constrains what is triggered, not every
  body that may execute: the planner includes each target's full upstream
  dependency closure and persistent cache state decides what reruns. No node
  downstream of those targets is planned.

Cycle detection is participation-scoped rather than a whole-graph gate. The
analysis reports nodes in SCCs of size greater than one plus self-loops, while
reachability, minima, maxima, sinks, and between remain meaningful elsewhere.
Execute up to is disabled when its upstream closure intersects a cycle;
Execute from onwards checks the upstream closure of its derived output
targets; Execute between checks its selected range. An unrelated cycle does
not hide or disable valid actions.

### 18. Multi-window and multi-user readiness

**Multi-window (one app, several OS windows, shared state).** A same-origin SharedWorker owns each live document's canonical snapshot, revision, and ordered patch log. Windows dispatch serializable commands and receive patches while derived state (elaboration, typing, layout) recomputes locally, so the render hot path never crosses IPC. Selection, viewport, and frozen execution-tab focus remain per-window view state; shared workspace focus always names a live tab. All windows use one durable `client_id` per backend connection, and normalized execution registrations and events are mirrored across the workspace so every view observes live runs. Electron main owns native-window assignment and durable bounds; browser-only launchers coordinate equivalent pop-out assignments over a same-origin channel.

**Multi-user (real-time collaboration on one workflow) - significant but additive, not a rewrite.** The classic rewrite-forcers are already absent by design: no shared mutable object graph, no positional arrays, no index-based links, no side-channel mutations. Stable UUIDs, ID-keyed values, and discrete commands with patches are the prerequisites for any sync scheme. The pragmatic path is a server-ordered command log (Figma-style: optimistic local apply, rebase to canonical order, last-writer-wins per property), which the per-entity/per-property document shape suits. Genuinely remaining work: selective per-user undo (the hard classic collab problem), a sync/presence/permissions server, and conflict UX. The execution model cooperates as-is: runs are snapshot-anchored objects keyed by `prompt_id`, so concurrent users queueing from one evolving document just produce independent frozen views.

**Binding guards (enforced from the initial contracts, cheap now, expensive to retrofit):**

1. Core packages never touch DOM or window-scoped globals - already a design rule; multi-window makes it load-bearing.
2. The document store remains a forest of ID-keyed entities with independently mergeable properties - no cross-entity denormalization, no order-dependent meaning outside explicit ordered lists.
3. Commands stay serializable (plain-data payloads, no closures/object references) and deterministic given document state - so they can cross IPC today and a sync log later.
4. Undo stays patch-based per document, keeping the door open to per-user selective undo.

### 19. Backend co-evolution: the post-rewrite target

A backend rewrite/refactor follows the frontend rewrite. The frontend is architected so that each backend modernization step **deletes frontend code instead of restructuring it**. The target state and the items that get simpler, collected from earlier sections:

- **V1 node schema retired (directional decision): everything - frontend and execution engine - speaks V3 (or its successor).** The frontend prepares by defining NodeSchema semantics against V3 and quarantining V1 support in one deletable adapter (section 2). Retirement is: delete the adapter, drop V1 golden fixtures, done. Node packs still authoring V1 defs at that point are the backend migration's problem (a V1->V3 shim can live server-side during its transition), not the frontend's.
- **Native schema endpoint (Dinkster backend).** Today's /object_info is V3 deliberately down-converted to the V1 wire shape for the old frontend's benefit; we parse that for now. Dinkster's object_info successor should emit a shape isomorphic to the frontend's normalized NodeSchema model: one ordered interface list (true interleave of inputs/widgets/sections, not required/optional/widget groups), real output IDs (no parallel arrays, no synthesized `out0`), full MatchType constraints on outputs (allowed_types is currently dropped on the wire), dynamic constructs as structured objects rather than marker-typed inputs, and a schema-version field. The normalized model in `@dinkster/core` (schema/model.ts) is the reference spec for that format; when it lands, the frontend swaps the adapter for a near-identity decoder.
- **Server accepts the unified workflow format directly** (section 16): the flat `{id: {class_type, inputs}}` prompt lowering disappears; the CompileArtifact's snapshot becomes the submission itself. Provenance maps simplify since runtime IDs can be the document's own stable IDs - subgraph flattening provenance stays (the engine may still flatten), but ID translation goes away.
- **Execution events keyed for multi-client** (risk 4): replacing client_id-only routing with per-prompt subscription or broadcast makes cross-window/cross-user live progress native; the Execution-object model consumes it unchanged (events already route by prompt_id).
- **Dynamic outputs** (section 3): count-bound families and stored heterogeneous descriptors are supported by Dinkster and the frontend; native links use compiler-resolved output IDs. Runtime-computed arity is not supported.
- **Parallel execution** (section 8): the frontend is display-ready for both forms before the backend ships either. Concurrent prompts on one server (today the queue is serial per server) need only backend scheduling work - Executions are already independent per prompt_id. Branch-parallel execution within one workflow (multiple nodes running at once, building on the async execution engine) needs only richer `progress_state`-style events - the per-node state map renders it with no frontend model change. Multi-backend fan-out works from the frontend alone via BackendConnection; a future shared-queue/cluster scheduler would slot in as another connection type.
- **Portable kernels** (section 9): backend executes declared GLSL/WGSL/WASM kernels as node implementations, making the mirror tier exact by construction.
- **Named nets/selectors stay frontend-side** (compiled away) even post-rewrite - pushing them into the engine buys nothing and splits one concept across two systems.

Sequencing guard: the frontend never blocks on any of these (each has a shipping fallback path), and none of them, when they land, invalidate a format or contract decision - that is what the initial contracts are for.

### 20. Testing strategy: headless-first, gesture-real, no pixel-hunting

The architecture's layering is what makes testing convenient: the further down the stack, the less machinery a test needs.

**Tier 1 - headless pure-TS (Vitest, no browser).** Document model, commands/undo, elaboration, type solver, subgraph flattening, named-net lowering, compiler + provenance, importer, replacement rules. This is where subgraph and dynamic-type correctness is proven, because these layers have zero DOM/canvas dependencies (a multi-window guard, section 17, doubling as a testability guarantee). Includes:
- Golden fixtures (schemas, workflows, prompts, event streams) as regression tests: fixture in -> expected CompileArtifact/elaborated interface out.
- Property-based tests (fast-check style): random valid command sequences preserve structural invariants; undo/redo round-trips restore exact document state; type solving is order-independent; import->save->import is a fixed point.
- The structural invariant checker runs as a test oracle in all of these.

**Tier 2 - scene-level tests (Vitest or jsdom, still no real browser).** The retained scene graph is renderer-neutral data (section 13), so layout and presentation are testable by building a scene from a document and asserting on primitives: row placement, paired lines, overflow rows, badge presence, would-run overlay membership, net collapse rendering. **Scene snapshots (JSON) are the primary visual-regression tier** - stable, diffable, no font/GPU flake - catching layout regressions more precisely than screenshots.

**Tier 3 - browser interaction tests (Playwright).** SolidJS is a non-factor here: Playwright is framework-agnostic and Solid emits plain DOM; Vite integrates via `webServer`. The canvas is the real problem - Playwright cannot query into a Canvas2D bitmap - solved by contract:
- **Test bridge**: an explicitly supported `window.__comfyTest` API resolving any semantic element ID (node, port, widget, badge, net endpoint, popover item) to screen coordinates + state, built on the same hit-region/spatial-index data the renderer already maintains. Tests then drive *real* pointer gestures (`page.mouse.down/move/up`) through the actual event pipeline - "drag output A to input B", "open subgraph badge popover, click Detach", "box-select, mute" - with no coordinate hardcoding.
- The offscreen accessibility list (section 13) gives Playwright queryable DOM for state assertions (selection, badges, error text) for free.
- A small pinned-environment `toHaveScreenshot` suite (one browser/OS, bundled fonts) covers actual paint quality; kept small because Tier 2 owns layout.

**Execution flows without a GPU.** The WS event normalization contract + recorded event-stream fixtures back a **fake backend server** that replays streams deterministically with controllable timing: tabs, frozen views, divergence badges, partial execution, error routing, and reconnect/history reconciliation all run in CI. A thin smoke suite against a real ComfyUI (managed via comfy-runner) runs on a slower cadence to catch contract drift. **Once the backend rewrite lands, this smoke suite is promoted to a full e2e gate**: real backend in CI, covering submit/progress/outputs/errors and eventually parallel-prompt and branch-parallel event streams - the fake backend stays for speed and for simulating timings a real backend can't produce on demand (races, disconnects, reordered events).

**Determinism rules**: RNG and clock are injected services (already required for seed controllers and selector random policies), so any test can pin them. Component-level shell tests use `@solidjs/testing-library` where a full page is overkill.

**Extension API tests**: the extension API implementation pack audit (rgthree/KJNodes/VHS/pysssss coverage) is executed as a test suite - each capability claim gets a Playwright or headless test against a sample extension, so API regressions surface mechanically.

### Diagnostics on the graph

Document diagnostics are projected onto node header badges and exact input-pin
rings without changing their raw severity. One composition step retains the
active tab's compile/submit-validation diagnostics, scene solver/widget
diagnostics, frozen artifact diagnostics, and bound execution errors before one
shared resolver projects them; a warning source therefore cannot replace or
mask a runtime error source. The projection is ephemeral view state: structured
refs select nodes only when their explicit graph id matches the current graph
(graph-less refs remain display-only), compiler/runtime occurrence anchors
select only the matching subgraph instance path, and port-only anchors are
qualified against the active graph instead of scanning graph-local node ids.
It is rebuilt when the compile/validation Problems owner, execution errors, or
per-scene solver/widget diagnostic sweep changes.

The filtering and visual semantics are explicit:

- `info` diagnostics do not produce graph badges.
- Error diagnostics use a red document-error badge and always block execution.
- A non-error may set ephemeral `blocksExecution: true`; it uses a separate
  orange blocking-warning badge. `compile.input.missing` sets this signal
  because the absent required API input can be rejected at submission even
  though warning severity remains part of its contract.
- Other anchored warnings, including widget-value and static-snapshot
  advisories, use an amber `W` badge. They remain visible but do not claim to
  block execution.

An anchor carrying `port` additionally projects to the exact elaborated input
pin id (`port#member` for dynamic members). The renderer receives only the
resolved per-port severity, never diagnostics: red denotes error, theme orange
denotes an execution-blocking warning, and badge amber denotes an advisory.
Error wins when several diagnostics share a pin. A diagnosed widget-backed pin
reveals even when it would normally wait for selection/hover, and the ring is
painted outside its ordinary typed body; selection/hover remain independent.
Compile artifacts record `inputSources` provenance from every backend wire
`apiName` to its exact source `PortRef`, including dynamic members and omitted
required inputs. Native `inputId` and legacy `extra_info.input_name`
submit-validation diagnostics resolve through this map alongside occurrence
provenance, so they use the same path as compile diagnostics rather than a
canvas-specific resolver or an unsafe wire-name guess.

The renderer also projects the already-derived badge identities onto the node
border; it does not inspect or reclassify diagnostics. Document errors paint a
2.5px red outline and blocking warnings paint a 2.5px outline using the same
theme orange as their badge. Advisory warnings remain badge-only. Border
precedence is missing schema, runtime execution error, document error, running,
blocking warning, other runtime state, then the default border. Selection and
hover rings remain outside this state border, and the bypass wash remains
inside it, so those independent signals stay legible.

Hover and click list the badge's node-local group through `problemDisplay`, so
current node and port names are shown while stable raw ids and messages remain
unchanged. `blocksExecution` is diagnostic metadata only: it is not document
data and is not emitted on the graph wire.

## Key risks / open questions

1. **Variadic/conditional subgraph boundaries** are exposure-deferred, but their representation, identities, and serialization are in the format from the initial contracts - the corner is designed out, the UI work is just later. Guard: never ship a boundary feature not already modeled in the format.
2. **Widget contract completeness**: the WidgetKind interface must be proven by porting the hardest core widgets (curve editor, bbox, webcam, image compare) through the public API before freezing it. Triage top custom-node packs to size what the contract must cover.
3. **Extension API scope creep vs. starvation**: too small and authors hack around it (old frontend failure mode), too big and it fossilizes. Mitigation: core dogfoods every registry; API additions driven by concrete extension requests.
4. **Cross-window live progress** limited by server's client_id routing; v1 accepts it, later options: history polling or a server-side broadcast opt-in.
5. **Remote combo security/caching policy** (arbitrary routes declared by nodes): now specified in the RemoteSource contract (section 10) - same-origin only, TTL respected, no auto-fetch on schema load. Implementation lands in dynamic interface implementation.
6. **Get/Set migration**: imported KJNodes Set/Get pairs should be converted to named nets by the importer (pattern-matched by class name) - nice-to-have, listed for execution UX implementation/extension API implementation.
7. **Shell framework ecosystem risk** (if SolidJS): smaller component ecosystem; contained because the shell surface is thin and the core/canvas/widget layers are framework-free.
8. **Legacy import fidelity**: positional `widgets_values` -> ID mapping depends on the *current* schema's widget order matching the schema the workflow was saved under; mismatches are surfaced as review diagnostics rather than silent misassignment, but very old workflows against changed nodes will need manual fixes. Mitigate with per-node-pack mapping tables for the most common historical schema changes.
9. **Dynamic outputs** derive from stored counts or descriptor literals, preserving the elaboration DAG constraint (no type feedback) and stable output identity. Metadata probe profiles are revalidated before execution; runtime-derived arity remains unsupported.
10. **Overflow-output placement**: decided - dedicated rows for overflow outputs; pin stack rejected as potentially confusing (may still be mocked once in initial implementation for reference). The row model survives either answer, so this is reversible if prototypes surprise us.
